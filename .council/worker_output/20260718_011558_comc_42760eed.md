# MiMo Round 1 — ZCode Goal-Drift Distillation

## 1. Core Thesis

Goal drift is not a single failure — it is the compound effect of three unguarded transitions: (a) the executor silently reinterprets the objective, (b) intermediate artifacts accumulate unverified assumptions, and (c) completion is self-asserted without independent evidence. The minimal fix is a **three-lock door** architecture: immutable objective lock, bounded task contracts, and a read-only guardian verdict on every completion claim. Everything else is noise until these three are proven.

## 2. Minimal Anti-Drift Architecture

### Roles (3 active + 1 passive)

| Role | Model | Mode | Frequency |
|------|-------|------|-----------|
| **Planner** | GPT-5.6-sol | Read-only; produces plan doc | Once per goal, re-invoked on REPLAN only |
| **Executor** | Qwen3.7-Max | Read-write; bounded to one task contract | Once per task |
| **Guardian** | GLM-5.2 | Read-only; verdicts on evidence | Once per task completion, once per 10-min cycle |
| **Watchdog** | Deterministic (no model) | Monitors native task state | Every 10 minutes |

Planner and Guardian must be different model families from Executor. Guardian is always read-only — it never edits code, only emits verdicts.

### What gets merged (not separate roles)

- Decomposition is folded into the Planner's output. The plan document contains both the high-level architecture and the bounded task contracts. Separate decomposer adds orchestration overhead with no proven value.
- "Reviewer" is absorbed by the Guardian role. The Guardian reviews code *and* progress evidence — splitting them doubles API calls for marginal benefit.

### What is explicitly NOT a role

- There is no "orchestrator model." Orchestration is a deterministic state machine (see §3). Using a model for orchestration is the primary source of agent bureaucracy.

## 3. State Machine and Completion Gate

### Goal State Machine

```
INIT → PLANNING → PLAN_LOCKED → EXECUTING → GUARDIAN_REVIEW
                                                  ├─ ACCEPT → (more tasks?) → EXECUTING
                                                  │                        → ALL_DONE → VERIFIED
                                                  ├─ CONTINUE → EXECUTING (same task, with guidance)
                                                  ├─ REPLAN → PLANNING
                                                  ├─ ROLLBACK → EXECUTING (prior checkpoint)
                                                  └─ ESCALATE → USER_DECIDES
```

### Completion Gate (hierarchical)

A task is "done" only when ALL of the following hold:

1. **Machine evidence**: Tests pass, linter clean, build succeeds — checked by deterministic tooling, not by any model.
2. **Guardian ACCEPT**: A read-only model from a different family inspects the diff + test output + acceptance criteria and emits ACCEPT. CONTINUE/REPLAN/ROLLBACK override any executor claim of done.
3. **No self-certification**: The executor cannot mark a task as complete. Only the Guardian can advance the state from GUARDIAN_REVIEW to EXECUTING (next task) or ALL_DONE.

The `goal.complete()` / verification step from ZCode Goal Mode serves as the final outer gate. The guardian verdict is the inner gate. Both must pass.

### Budget enforcement

Each task contract carries a `max_turns` field (default 6). If executor exceeds it, the task is force-aborted to GUARDIAN_REVIEW. No task contract allows "unlimited iteration."

## 4. Artifact / Schema Design

### Immutable Artifacts (written once, never edited)

```
goal_manifest.md          — objective, non-goals, acceptance criteria, risks
plan.md                   — architecture, task contracts, dependency graph
checkpoints/
  task_001_completed.diff — frozen diff at task completion
  task_001_guardian.md    — guardian verdict with evidence references
```

### Mutable Artifacts (updated during execution)

```
task_current.md           — active task contract (bounded scope)
progress.md               — task status log (append-only)
watchdog_state.json       — last_check timestamp, hung_count, escalation_flag
```

### Task Contract Schema

```yaml
task_id: "task_001"
title: "Implement login endpoint"
acceptance_criteria:
  - "POST /api/login returns 200 with valid credentials"
  - "POST /api/login returns 401 with invalid credentials"
  - "Unit tests pass for auth module"
max_turns: 6
depends_on: []
files_in_scope:
  - "src/auth/login.ts"
  - "tests/auth/login.test.ts"
non_goals:
  - "Do not modify registration flow"
```

### Guardian Verdict Schema

```yaml
task_id: "task_001"
verdict: "ACCEPT"  # ACCEPT | CONTINUE | REPLAN | ROLLBACK | ESCALATE
evidence:
  tests_passed: true
  linter_clean: true
  diff_review: "Scope matches contract. No extraneous changes."
  drift_detected: false
notes: ""
```

## 5. Model Routing Policy

### Routing table (task-type → model)

| Task Type | Primary Model | Escalation |
|-----------|---------------|------------|
| Planning / architecture | GPT-5.6-sol | Never (top of chain) |
| Routine implementation (CRUD, boilerplate, tests) | Qwen3.7-Max | → GPT-5.6-sol on REPLAN |
| Complex implementation (multi-module, state machines) | Qwen3.7-Max | → GPT-5.6-sol if max_turns hit |
| Guardian review | GLM-5.2 | → DeepSeek-V4-Pro on ESCALATE |
| Security-sensitive task | DeepSeek-V4-Pro | Never (always use for security scope) |
| UI / frontend task | MiMo-V2.5-Pro | → Qwen3.7-Max if complexity high |
| Debugging / error recovery | Qwen3.7-Max | → GPT-5.6-sol if 2 fixes fail |

### Routing rules

1. **Task type is determined by the Planner** at plan time and recorded in the task contract. The executor does not choose its own model.
2. **Escalation is one-way up**: MiMo → Qwen → GPT. No model can downgrade.
3. **Guardian is always from a different family** than the Executor. If executor is Qwen, guardian is GLM. If executor is MiMo, guardian is GLM or DeepSeek.
4. **Cost ceiling**: If total API cost exceeds 3× the initial estimate, force ESCALATE to USER_DECIDES. Prevents runaway spending.
5. **Kimi-K3 is excluded** from routine routing — insufficient proven reliability. Available only on explicit user override.
6. **No model acts as orchestrator** — the state machine is deterministic code, not an LLM call.

## 6. Safe 10-Minute Watchdog Policy

### Verified constraints (do not violate)

- `metadata.json.updatedAt` is NOT a live heartbeat — it only updates on terminal write.
- BackgroundTaskTracker injects `<task-notification>` on completion — this is the primary signal.
- Windows Task Scheduler can trigger externally but cannot wake the same model turn.
- No cron/heartbeat/notification hooks exist in the current runtime.

### Watchdog design

**Implementation**: A deterministic plugin (not a model) that runs on a 10-minute interval using the native scheduler/task-registry (requires exposing `TaskList` and `TaskGet` — currently blocked, see rollout §8).

**Behavior**:

```
every 10 minutes:
  1. Call TaskList to get active tasks
  2. For each active task:
     a. If task has <task-notification> → state is DONE, advance to GUARDIAN_REVIEW
     b. If task age > task_deadline_minutes (from task contract, default 30):
        - hung_count += 1
        - If hung_count >= 2: force-abort task, advance to GUARDIAN_REVIEW with ESCALATE
        - If hung_count == 1: log warning, continue waiting
     c. If no <task-notification> and age < deadline: do nothing (not hung, just running)
  3. Write watchdog_state.json
```

**What the watchdog does NOT do**:
- It does not check `metadata.json.updatedAt` as a heartbeat (per verified fact).
- It does not terminate tasks on first timeout — a single missed cycle is not evidence of a hang.
- It does not use any model — it is pure deterministic logic.
- It does not restart the orchestrator — that is a separate concern.

**Interim workaround** (until TaskList/TaskGet are exposed):
- Poll `<task-notification>` events from the session log directly.
- Use a file-based heartbeat: executor writes `task_current.md` on each turn start. If the file's mtime exceeds 15 minutes and no notification exists, flag as potentially hung.
- Accept that this is less reliable and increase hung_count threshold to 3.

## 7. Failure Modes and Rejected Overengineering

### Failure modes identified

| Failure | Cause | Mitigation |
|---------|-------|------------|
| Executor silently drifts from objective | No immutable reference | goal_manifest.md is immutable; Guardian checks against it |
| Guardian rubber-stamps | Same model family as executor | Different family enforced; ESCALATE if too-permissive (100% accept rate triggers user alert) |
| Infinite loop on CONTINUE | Guardian keeps saying CONTINUE | max_iterations_per_task = 3 CONTINUE verdicts, then force REPLAN |
| Planner over-analyzes | GPT-5.6-sol scope creep | Plan doc capped at 200 lines; task contracts capped at 10 per plan |
| Watchdog false-positive hang | Slow but legitimate work | Two-strike policy (hung_count >= 2) before escalation |
| Budget blowout | Unbounded retries | 3× cost ceiling with USER_DECIDES |
| Rollback loses work | Checkpoint too old | Checkpoint after every ACCEPT; rollback goes to most recent |

### Rejected as overengineering

1. **Separate decomposer role** — adds an orchestration hop with no proven value. The Planner already decomposes.
2. **Continuous heartbeat polling** — BackgroundTaskTracker already provides terminal events. Polling is wasteful and unreliable.
3. **Nested subagent orchestration** — current runtime does not support it reliably. Adding it would require undocumented API assumptions.
4. **Model-based orchestration** — a model choosing which model to call next is agent bureaucracy. The state machine is deterministic.
5. **Semantic similarity scoring for drift detection** — adds latency and false positives. Guardian comparing diff to acceptance criteria is sufficient and more reliable.
6. **Dedicated "reviewer" separate from Guardian** — doubles cost for marginal signal. Guardian does both code review and progress verification.
7. **Cron-based scheduling inside the agent runtime** — hooks don't support it, and external task scheduler is more reliable.

## 8. Staged Rollout with Acceptance Criteria

### Phase 1: Foundation (no new tool exposure needed)

**What**: Implement goal_manifest.md, plan.md with task contracts, and Guardian verdicts using existing ZCode Goal Mode + session artifacts. Watchdog uses file-mtime workaround.

**Acceptance criteria**:
- [ ] Goal Mode persists through 20+ turns without losing objective
- [ ] Guardian rejects at least 1 intentional drift scenario in test
- [ ] Completion gate blocks self-certification in test
- [ ] Watchdog detects a simulated hung task within 20 minutes

### Phase 2: Deterministic Orchestration

**What**: Implement the state machine as deterministic code (not an LLM). Route models based on task contract type. Enforce max_turns per task.

**Acceptance criteria**:
- [ ] State machine handles all 7 transitions without model involvement
- [ ] Model routing matches table in §5 for 5 test tasks
- [ ] max_turns force-aborts correctly in test
- [ ] CONTINUE limit (3) triggers REPLAN correctly

### Phase 3: Native Watchdog (requires TaskList/TaskGet exposure)

**What**: Replace file-mtime workaround with native task registry polling. Implement two-strike hang detection.

**Acceptance criteria**:
- [ ] TaskList returns accurate active/completed status
- [ ] Watchdog detects hung task without false positive on slow legitimate work
- [ ] Watchdog force-abort advances to GUARDIAN_REVIEW with ESCALATE
- [ ] watchdog_state.json is auditably correct after 10 cycles

### Phase 4: Cost and Escalation Controls

**What**: Implement 3× cost ceiling. Implement Guardian accept-rate monitoring. Route security tasks to DeepSeek.

**Acceptance criteria**:
- [ ] Cost ceiling triggers USER_DECIDES at 3× estimate
- [ ] Guardian with 100% accept rate over 5+ reviews triggers alert
- [ ] Security-scoped tasks route to DeepSeek automatically
- [ ] Escalation is one-way up (MiMo → Qwen → GPT verified)

---

## Most stealable ideas

1. **Three-lock door**: Immutable objective, bounded task contracts, and independent guardian verdict. Any two of three are bypassable; all three together prevent drift without orchestrator overhead.

2. **CONTINUE budget**: Guardian gets exactly 3 CONTINUE verdicts per task before the system forces REPLAN. This prevents the "keep trying" infinite loop while still allowing reasonable retry.

3. **Cost ceiling as a hard gate**: 3× estimated cost triggers USER_DECIDES regardless of progress. This is the only reliable defense against runaway agent spending, and it works without any model involvement.

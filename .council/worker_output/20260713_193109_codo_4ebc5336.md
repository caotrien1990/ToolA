## Confirmed zone-assignment defect
- clm_librarian_capture.py owns only the original schema and its insert_turn statement does not write zone or source_type and does not upsert zone_index. Evidence: capture lines 122-176 and 430-455.
- clm_librarian_api.py later adds zone with DEFAULT Z3 and source_type with DEFAULT manual. It performs a one-time/backfill correction to Z1/session for Claude and Codex only when columns are newly added, or later only when both values are blank. Evidence: API lines 553-603.
- Once those columns already exist, each newly captured Claude/Codex row inherits Z3/manual. Because both values are nonblank, repeated API initialization does not correct it. API initialization then inserts the same Z3 value into zone_index when the index row is absent.
- Live DB evidence confirms the predicted footprint: Claude has 101 Z3/manual rows and Codex has 1 Z3/manual row. By contrast, intended session rows are Z1/session. Current totals are raw_turns=44,695 and zone_index=44,694, so one raw row is also missing from zone_index at query time.
- This is a direct write-path/schema-contract mismatch, not merely a UI counting issue. New scheduled capture can continue adding misclassified Z3/manual rows.

## Related hazards
- The capture test suite validates parsing, tail windows, dedup, and project extraction but never asserts zone, source_type, or zone_index. Evidence: clm_librarian_capture_test.py lines 61-190.
- Several tests construct argparse.Namespace without skip_prune even though scan_writer reads args.skip_prune at capture line 599; current test execution was not run in this read-only task, so the actual failure status is unknown / not verified.
- zone_paths.json is disabled and review_required, but its draft taxonomy maps ToolQ to Z3. It is not the cause of scheduled session capture because the capture writer does not read this file. Enabling it would create a separate taxonomy hazard.

## Minimal fix contract
1. Make capture initialization schema-aware: ensure zone/source_type/zone_index exist before insert, without duplicating divergent schema logic if a shared migration helper can be used.
2. Insert Claude/Codex capture rows explicitly as zone=Z1 and source_type=session; upsert zone_index in the same transaction using the inserted raw_turn id and an intentional subzone, or no subzone if that is the canonical contract.
3. Add a regression test against a migrated schema that proves a newly captured Claude row and Codex row are Z1/session and have matching zone_index rows. The test should encode why: schema defaults must never decide session taxonomy.
4. Backfill only the proven bad population: writer in Claude/Codex, zone=Z3, source_type=manual, with backup and before/after counts. Do not broadly relabel all Z3 or all manual rows.
5. Verify active-row counts with deleted_at IS NULL and verify no live Claude/Codex session row remains Z3/manual or lacks zone_index.

## Verdict
The primary capture-side cause of zone mislabeling is confirmed: the scheduled capture insert omits modern zone metadata, so the migrated DB defaults new session turns to Z3/manual and later propagates that value into zone_index. No ToolQ source or database mutation was performed.

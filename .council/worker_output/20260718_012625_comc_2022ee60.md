## 2. What I Steal

### Steal 1: File-allow-list PreToolUse hook (from Qwen)

Qwen's `scope.files_allow` enforcement on write tools is the single most impactful mechanism across all three Round 1 proposals. It is:
- **Deterministic**: pure hook logic, no model involved.
- **Zero-cost**: fires on every write tool call but adds no API calls.
- **Preventive**: stops drift at the source ("I'll just fix this adjacent thing") rather than detecting it after the fact.
- **Implementable today**: ZCode supports PreToolUse hooks.

I adopt this as the **primary anti-drift mechanism** — more important than Guardian review, which becomes the second line of defense. The file-allow-list is the lock; Guardian is the auditor who checks whether the lock held.

### Steal 2: Three-tier watchdog honesty (from Qwen)

Qwen's T1/T2/T3 tiering is the only design that honestly separates:
- **T1** (event-driven, native `<task-notification>`) — what works today.
- **T2** (external timer, Windows Task Scheduler) — what works as interim workaround.
- **T3** (contract deadline check at Guardian invocation) — what enforces actual policy.

Cozo's watchdog has cleaner state names (RUNNING→OVERDUE→SUSPECTED_HUNG→HUNG) but assumes a plugin that doesn't exist and offers no interim path. I adopt Qwen's tier structure and Cozo's state naming, combining them.

### Steal 3 (minor): Cross-family disagreement rate as Guardian quality signal (from Qwen)

Qwen's criterion that "cross-family disagreement rate ≥ 15% (else Guardian is rubber-stamping)" is a measurable quality gate for the Guardian role itself. I adopt this as a Phase 3 acceptance criterion.

## 3. What I Reject or Repair

### Reject 1: Qwen's `drift_ledger.scope_tokens` — factual error in design

Qwen proposes `"scope_tokens_budget": 1.0, "scope_tokens_consumed": 0.0` but never defines how "scope tokens" are measured. What is a "token" of out-of-non-goal work? Is it a literal LLM token? A file touched? A line changed? A semantic similarity score?

This is **unimplementable as written**. There is no reliable, deterministic way to measure "how much the executor drifted" in real-time. The concept is sound (budget-based drift tolerance) but the metric is undefined.

**Repair:** Replace `drift_ledger` with a **concrete, countable budget**: `out_of_scope_writes` (number of PreToolUse hook rejections for files outside `files_allow`). This is deterministic, zero-cost, and measurable. If the executor tries to write outside its allow-list 3+ times in one task, that's a drift signal that routes to Guardian for early review. This is strictly more implementable than semantic token counting.

### Reject 2: Cozo's mixed-level verdict enum — structural error

Cozo's verdict enum includes both `ACCEPT_TASK` (task-level) and `ACCEPT_MISSION` (mission-level) in the same Guardian output. This conflates two different state transitions:
- `ACCEPT_TASK` advances to the next task or to `ALL_DONE` check.
- `ACCEPT_MISSION` is the final goal-level acceptance.

If the Guardian emits `ACCEPT_MISSION` when tasks remain, or `ACCEPT_TASK` on the final task without checking mission-level criteria, the state machine has a bug. Cozo's completion conjunction partially mitigates this, but the enum itself is error-prone.

**Repair:** Split into two distinct verdict sets:
- **Task verdicts**: `ACCEPT_TASK`, `CONTINUE`, `REPLAN`, `ROLLBACK_TASK`, `ESCALATE`
- **Goal verdict**: `GOAL_DONE` (only emitted after all tasks have `ACCEPT_TASK` + machine checks pass)

This matches Qwen's cleaner separation. The Guardian never emits `GOAL_DONE` unless the four-point conjunction holds.

### Reject 3: Qwen's Guardian emitting `OVERDUE` as a verdict type — conflation

Qwen's watchdog design has the Guardian emit `OVERDUE` as a verdict. But `OVERDUE` is a time-based signal, not a code-quality assessment. Having the Guardian emit it conflates two concerns:
- "This task is taking too long" (watchdog concern)
- "This code doesn't meet the acceptance criteria" (Guardian concern)

**Repair:** The watchdog produces an `OVERDUE` **signal** (not a verdict). This signal is an input to the Guardian's next invocation, where the Guardian considers it alongside code quality. The Guardian's verdict remains in the code-quality domain (`CONTINUE`, `REPLAN`, `ROLLBACK_TASK`, `ESCALATE`). The watchdog signal doesn't auto-escalate — it reduces the Guardian's tolerance for weak evidence.

### Preference disagreement: Qwen's `drift_ledger` as budget concept

Even with the scope_tokens metric rejected, the *concept* of a drift budget is valuable. I preserve it in simplified form (out-of-scope write count) rather than discarding it entirely.

## 4. Improved Architecture

### Core principle (refined from R1)

Drift is prevented by three layers working in sequence, not detected by one expensive layer at the end:

1. **Boundary enforcement** (deterministic, zero-cost): file-allow-list PreToolUse hook prevents the most common drift — writing outside task scope.
2. **Task-bounded execution** (model, contained): executor works within one task contract, with max_turns and out-of-scope-write budget.
3. **Independent verification** (cross-family model + machine): Guardian reviews evidence against acceptance criteria at task boundaries only.

### Roles (3 active + 1 deterministic, unchanged from R1 but with file-allow-list added)

| Role | Model | Mode | What changed from R1 |
|------|-------|------|---------------------|
| **Planner** | GPT-5.6-sol (hard) / Qwen (standard) | Read-only | Now also specifies `files_allow` per task contract |
| **Executor** | Qwen (default) / MiMo (UI) / DeepSeek (security) | Bounded write | Now constrained by file-allow-list hook + out-of-scope budget |
| **Guardian** | GLM-5.2 (default) / DeepSeek (security-scoped) | Read-only | Now receives watchdog signals as input; has CONTINUE budget |
| **File-allow-list hook** | Deterministic (no model) | PreToolUse | NEW — primary anti-drift layer |

### What stays merged
- Decomposer → Planner (same as R1 and both peers agree).
- Watchdog → deterministic signal provider (not a Guardian verdict, not a separate role).
- Test runner → tool (not a role).

### What stays excluded
- No orchestrator model. The state machine is deterministic code.
- No per-tool-call Guardian review (too expensive, too slow).
- No semantic similarity scoring for drift detection.
- Kimi-K3 excluded from routine routing (insufficient proven reliability).

## 5. Final State Machine and Completion Formula

### State machine

```
INIT
  │
  ▼
PLANNING ──────────────────────────────────────────────────┐
  │ plan_ready                                              │
  ▼                                                         │
PLAN_REVIEW ── reject ──► ESCALATE_TO_USER                  │
  │ accept                                                  │
  ▼                                                         │
EXECUTING(t) ◄──────────────────────────────────────────┐   │
  │                                                     │   │
  │ [file-allow-list hook blocks out-of-scope writes]   │   │
  │ [max_turns enforced; out-of-scope writes tracked]   │   │
  │                                                     │   │
  │ task_done(t) + evidence.json written                │   │
  ▼                                                     │   │
BOUNDARY_GATE                                           │   │
  │                                                     │   │
  ├─ ACCEPT_TASK ─► (more tasks?) ─► EXECUTING(next t) ┘   │
  │                  (no more)  ─► GOAL_GATE                 │
  ├─ CONTINUE ──► (CONTINUE_count < 3?) ─► EXECUTING(t) ───┘
  │               (CONTINUE_count >= 3) ─► REPLAN ──────────┘
  ├─ REPLAN ────► PLANNING ────────────────────────────────┘
  ├─ ROLLBACK_TASK ─► EXECUTING(t, prior checkpoint) ──────┘
  └─ ESCALATE ──► USER_DECIDES
                                      │
GOAL_GATE ◄───────────────────────────┘
  │ [four-point conjunction checked by machine]
  ├─ all pass ──► DONE
  └─ any fail ──► BOUNDARY_GATE (with failed criteria flagged)
```

### Completion formula (failed-closed conjunction)

```
GOAL_DONE = ALL of:
  1. Every task has ACCEPT_TASK verdict from Guardian
  2. Every acceptance criterion maps to a machine-check result (test exit 0, linter exit 0, etc.)
  3. Guardian's final verdict is GOAL_DONE (not ACCEPT_TASK — the latter closes one task, not the goal)
  4. Zero unresolved ESCALATE verdicts
  5. Out-of-scope write count across all tasks < budget (default: 5 per goal)

If ANY condition fails → fail closed to BOUNDARY_GATE or REPLAN.
Executor cannot self-certify any of the five conditions.
```

### CONTINUE budget (anti-infinite-loop)

- Max 3 CONTINUE verdicts per task.
- On 3rd CONTINUE: force REPLAN with reason "executor unable to satisfy acceptance criteria within turn budget."
- This is a hard limit, not a soft suggestion. Guardian cannot override it.

### Out-of-scope write budget (anti-drift counter)

- File-allow-list hook tracks rejections: `out_of_scope_writes` counter per task.
- On 3rd rejection in one task: force early Guardian review (don't wait for task_done).
- On 5th rejection across the entire goal: ESCALATE to user.
- This replaces Qwen's vague `scope_tokens` with a concrete, deterministic metric.

## 6. Final Watchdog Contract

### Three-tier design (Qwen's structure + Cozo's state names)

| Tier | Mechanism | Status | What it does |
|------|-----------|--------|-------------|
| **T1 — Event-driven** | Native `<task-notification>` | **Available today** | Authoritative terminal signal. Leader wakes on notification, reads task state, advances to BOUNDARY_GATE. No polling. |
| **T2 — External timer** | Windows Task Scheduler writes `watchdog/<task_id>.tick` every 10 min | **Available today (workaround)** | Leaves a signal file for the next leader turn. Cannot wake the same model turn. If tick file exists at next leader turn, leader compares elapsed time to task contract deadline. |
| **T3 — Contract deadline** | Guardian reads `deadline_minutes` from task contract at invocation | **Available today** | Guardian checks task-start timestamp vs. deadline. If overdue, Guardian's evidence tolerance increases (requires stronger justification for CONTINUE/ACCEPT, may emit REPLAN or ESCALATE). |

### Watchdog state machine (per-task)

```
RUNNING ──(tick file age > deadline_minutes AND no notification)──► OVERDUE
OVERDUE ──(2 consecutive overdue ticks AND no notification)───────► SUSPECTED_HUNG
SUSPECTED_HUNG ──(tracker confirms no progress OR process dead)───► HUNG
HUNG ──► force-abort task, advance to BOUNDARY_GATE with ESCALATE
RUNNING ──(<task-notification> received)──────────────────────────► DONE (advance to BOUNDARY_GATE)
```

### What the watchdog does NOT do (prohibited)

- Does NOT check `metadata.json.updatedAt` as heartbeat (verified fact 5).
- Does NOT use CronCreate/CronList (verified fact 6 — not exposed).
- Does NOT attempt to wake the same model turn via external scheduler.
- Does NOT run on a model — it is pure deterministic logic or file-based signals.
- Does NOT terminate tasks on first timeout — SUSPECTED_HUNG requires 2 overdue ticks.
- Does NOT restart the orchestrator (separate concern).

### Plugin-dependent behavior (future, not current)

If scheduler/task-registry tools become available:
- T2 upgrades from "external schtasks + tick file" to "native 10-minute wakeup querying TaskList/TaskGet."
- Watchdog can delete its own watcher on terminal state (currently manual).
- T1 can be supplemented with proactive TaskList polling for faster detection.

This is documented as future work, not current capability.

## 7. Model Routing and Escalation

### Routing table

| Task shape | Executor | Guardian | Escalation |
|-----------|----------|----------|-----------|
| Standard code (CRUD, feature, refactor) | Qwen3.7-Max | GLM-5.2 | → GPT-5.6-sol if 2 boundary gate failures |
| UI/frontend iterative loop | MiMo-V2.5-Pro | GLM-5.2 | → Qwen if 2 loops fail |
| Security/correctness-sensitive (auth, crypto, migration) | DeepSeek-V4-Pro | GLM-5.2 | → user ESCALATE (never downgrade security model) |
| Hard planning (ambiguous scope, >6 tasks) | Planner=GPT-5.6-sol | GLM-5.2 | N/A (GPT is top of chain) |
| Repo-wide retrieval/impact analysis | GLM-5.2 as executor | Qwen | → Kimi-K3 only if multimodal/large-context needed |

### Escalation rules (deterministic, not vibes)

1. Executor fails 2 consecutive Boundary Gates on same task → escalate executor one tier (MiMo→Qwen, Qwen→GPT).
2. Guardian emits REPLAN twice in one goal → swap planner to GPT-5.6-sol regardless of prior choice.
3. Guardian's CONTINUE count hits 3 on any task → force REPLAN (Guardian cannot override).
4. Out-of-scope write count hits 5 across goal → ESCALATE to user.
5. Budget (total API cost) exceeds 3× initial estimate → ESCALATE to user (from R1, retained).
6. Kimi-K3 and DeepSeek-V4-Pro are not used "because they exist" — only for shapes above.
7. **No model can downgrade its own escalation.** If Qwen was escalated to GPT, Qwen does not resume.

### Guardian family separation (non-negotiable)

- Guardian must be from a different model family than the Executor.
- If executor is Qwen → guardian is GLM or DeepSeek.
- If executor is MiMo → guardian is GLM or DeepSeek.
- If executor is DeepSeek → guardian is GLM (never the same family).

## 8. Minimal Rollout

### Phase 1: File-allow-list hook (highest leverage, lowest effort)

**What:** Implement `scope.files_allow` enforcement on write tools via PreToolUse hook. No Guardian, no Goal Mode changes, no model routing.

**Acceptance criteria:**
- [ ] In 10 replay tasks, executor attempts to edit outside allow-list fail 100% of the time.
- [ ] Goal completion rate ≥ 70% (some tasks need contract expansion flow).
- [ ] Hook adds <1ms latency per tool call (deterministic check).

**Why this first:** This is the single highest-leverage mechanism. It prevents the most common drift pattern at zero model cost. Everything else builds on this foundation.

### Phase 2: Goal Mode + task contracts + completion gate

**What:** Implement `goal.json`, `tasks/<id>.contract.json`, `tasks/<id>.evidence.json`. Machine-only four-point completion gate (§5). CONTINUE budget (max 3 per task). Out-of-scope write counter.

**Acceptance criteria:**
- [ ] 20 replay tasks; goal completion ≥ 80%.
- [ ] Zero cases of executor self-certifying completion without Guardian + machine pass.
- [ ] CONTINUE budget triggers REPLAN on 3rd CONTINUE in 100% of synthetic tests.
- [ ] Out-of-scope counter triggers early Guardian review on 3rd rejection.

### Phase 3: Cross-family Guardian at task boundaries

**What:** Add GLM-5.2 (and DeepSeek for security shape) as read-only boundary reviewer. Verdict enum enforced. Watchdog T2+T3 active.

**Acceptance criteria:**
- [ ] Guardian produces all 5 task verdict types + GOAL_DONE across synthetic scenarios.
- [ ] Cross-family disagreement rate ≥ 15% (else Guardian is rubber-stamping, from Qwen).
- [ ] Watchdog correctly identifies OVERDUE tasks in ≥ 8 of 10 forced-slowdown tests.
- [ ] No false hung declarations from stale metadata.

### Phase 4: Model routing + escalation controls

**What:** Routing table from §7. All escalation rules wired. Budget ceiling (3× estimate → user ESCALATE). Guardian accept-rate monitoring.

**Acceptance criteria:**
- [ ] Correct model routing ≥ 90% across 20 test tasks (10 UI-iterative, 10 security-scoped).
- [ ] Escalation rules fire correctly in synthetic failure scenarios.
- [ ] Budget ceiling triggers USER_DECIDES at 3× estimate.

### Phase 5 (future): Native watchdog upgrade

**What:** If scheduler/task-registry tools become available, replace T2 external workaround with native 10-minute wakeup. Implement watchdog self-cleanup on terminal state.

**Acceptance criteria:**
- [ ] TaskList returns accurate active/completed status.
- [ ] Watchdog detects hung task without false positive on slow legitimate work.
- [ ] No slow healthy task killed from stale metadata.

## 9. Residual Disagreements

The council should not flatten these into false consensus:

1. **Drift budget metric:** I replaced Qwen's vague `scope_tokens` with concrete out-of-scope write counts. Qwen may argue this misses semantic drift (executor writes *within* allowed files but toward wrong objective). The file-allow-list catches file-level drift but not intent-level drift. The Guardian is the only check for intent-level drift — and that's by design. If the council wants intent-level prevention, that requires a model in the loop on every write, which I reject as too expensive.

2. **Guardian verdict for time-based signals:** I separated the watchdog's `OVERDUE` signal from the Guardian's code-quality verdicts. Qwen may prefer the Guardian to emit `OVERDUE` directly. The risk of Qwen's approach: conflating "this is slow" with "this is wrong" leads to false escalation. The risk of my approach: the Guardian might ignore the `OVERDUE` signal and emit `CONTINUE` anyway. The CONTINUE budget (max 3) mitigates my approach's risk.

3. **Planner model selection:** Cozo uses GPT-5.6-sol for all planning. I allow Qwen for standard planning (cheaper, faster). This is a cost/speed tradeoff. GPT for all planning is safer but more expensive. The council should decide based on observed planning quality variance between GPT and Qwen for non-ambiguous tasks.

4. **Rollback granularity:** Cozo allows rollback on "harmful divergence." Qwen ties rollback to per-task `rollback_trigger` conditions defined at plan time. I prefer Qwen's approach (deterministic, pre-defined) but acknowledge that some harmful divergence is only visible to the Guardian at review time, not predictable at plan time. The council should decide whether rollback triggers are plan-time-only or Guardian-discretionary.

5. **Kimi-K3 exclusion:** I excluded Kimi-K3 from routine routing (same as R1). If the council has evidence of Kimi-K3 reliability in production, this can be revisited. Until then, excluding unproven models from the default routing table is the conservative choice.

## 2026-08-21 — B021, two payloads that described their own contents wrongly

- **`git_status` described every file twice.** Measured live at gen `cac7187da50d`: 126,770 bytes, **truncated by the transport**, 270 records — and each record carried `raw` (the porcelain line) beside `record_type`/`xy`/`sub`/`path`/`orig_path`, which are the fields parsed *out of* it. ~71% of a record's bytes were a second copy of the same information, on the one *unbounded* part of the payload. The earlier B-series fix capped the record count and reported the cap honestly (`records_total`/`records_truncated`); the duplication survived it because capping made the payload smaller without making any *record* smaller.
- **The constraint that shaped the fix:** `state_hash` is a sha256 over `{'branch','records'}` and callers hold it *between* calls as an optimistic lock — `git_stage` refuses with `GIT_STATE_STALE`, `git_stale_check` reports `state_hash_mismatch`. Hashing the tidied records would have shifted every hash at once, so every lock a caller was holding would read as a concurrent modification that never happened. `raw` is dropped from the **response**; the **hash input keeps it**. *Tidying a payload must not be a protocol change.*
- **Probing the fix found two defects nobody had reported, and one of them was a crash.** In `-z` mode a rename/copy record (type `2`) is **two NUL-separated fields** — the record, then the original path — because a path cannot carry the tab that separates them in the non-`-z` format; `git-status(1)` documents this. The splitter treated the second field as a record of its own, so every rename produced a **phantom record** (`{'record_type': 'o', 'raw': 'old.txt'}`) that was counted in `counts['changed']`, and `orig_path` was **always `''`**. Worse, when the old path began with `u`, `1`, `2` or `!` the phantom was parsed as an unmerged/ordinary/ignored record and `rec.split(' ',10)[10]` raised **IndexError**: measured, `git mv util.py helper.py` made `git_status` **raise**, and since `git_stage` and `git_commit` both call `status()` first, all three tools went down on a rename of any file named `util.py`, `1.txt`, `2.txt`. The two fields are now rejoined with a **tab** — the shape the type-2 parser already expected — and an unrecognised record keeps its own line under `unparsed` instead of raising, so a future porcelain change cannot take these three tools offline.
- **`module_deps` answered `count=12`, `truncated=True` and `total_count=0` in one breath.** Those are the two fields a paginating caller chooses between, and they disagreed: `total_count` said "nothing here", `truncated` said "keep asking". Root cause: the two were **set independently**, and `module_deps` set neither — it inherited the initializer `0` and the shared tail's `if len(res) >= limit: truncated = True`. `total_count` is now the **pre-cap population** per branch (a `COUNT` over the *same predicate* as that branch's LIMIT-ed `SELECT`, `DISTINCT` included) and `truncated` is **derived** from it, offset-aware: `truncated iff offset + count < total_count`. One number, not two that can contradict. `impact_scope` is the single exemption — it answers one synthetic row whose `truncated` reports the **trace-depth cap**, so deriving it from 1-of-1 would report a blast radius that dropped files at `GRAPH_CONTEXT_MAX_FILES` as complete.
- **The docstring documented the bug as intended behaviour** — *"total_count is the true population for paginated templates (orphan_symbols); 0 otherwise"* — so a reader checking whether `total_count=0` was a defect would have closed the report. Rewritten, and pinned by a test. **Documentation that describes a bug as a feature is part of the bug.**
- **The rule B021 leaves behind: a fixture too small to distinguish the mutant is a test that measures nothing.** The first cut was 13 green tests and **three mutants walked through them**. `total_count` falling back to `0` survived because nothing asserted on `impact_scope` — the *only* branch that reaches the fallback — so `count=1 total_count=0`, the exact reported contradiction, would have shipped in the template the fix deliberately exempted. Counting **raw edges** instead of `DISTINCT` pairs survived because every fixture had one import per file, where the two counts happen to agree; a file importing the same module twice gives 2 edges for 1 pair, and the mutant then keeps `truncated` true on a **complete** read — the reported bug pointing the other way, a caller looping forever on the same last page. Counting `_all_eps` instead of `_prod_eps` survived for the same reason. 3 tests were added for exactly those, plus one for the capped blast radius.
- **Two of my own tests were wrong, not the fix.** `assert "state_hash_mismatch" not in matched["stale"]` raised `TypeError: argument of type 'bool' is not iterable` — `stale` is a bool, the named causes live in `reasons`; read as a container it would have asserted nothing on the happy path. And asserting that rewriting an already-`.M` file moves `state_hash` was **false before the fix too** (porcelain is byte-identical for a content-only edit), so it measured git's output rather than the lock. Both fixed, both now carry the reason in the test.
- 16 tests added, `tests/test_payload_says_each_thing_once_b021.py`. Mutation-verified with 6 mutants across the two files, each failing exactly the tests written for it: `raw` back in the response → 2; the `-z` rejoin removed → 1; hashing the tidied records → 1; `total_count` falling back to 0 → 1; `module_deps` not counting → 1; `truncated` back to `len(res) >= limit` → 1. One mutant silently failed to apply (tab escaping) and printed 12 passed — which reads exactly like a surviving mutant; caught and redone by line index. **A mutant that did not apply is not a mutant that survived.**

# CHANGELOG

## 2026-08-21 — JS-repo audit: five defects fixed, 39 tests added

- Audited [A]'s analysis tools against a **non-Python** repo (41 JS files) for the first time. Every one of the five defects found shares a shape: a tool that could not do something answered as though it had — the engine fell back without saying so, the glob was resolved and discarded, the validator passed a file it never opened, the extractor emitted a key that could never match, the index reported success while leaving rows behind. None errored; every one returned `ok`. Registered as B011-B015 in KNOWN_BUGS.md, with the audit technique that actually found them written up as MAINTENANCE_DOCTOR.md Entry 7.
- B011: `cbm_status` reported `stale_files: 24` immediately after a full index reporting `files_unchanged: 2`, and repeating the index never moved the number. Two counters over two populations — the index walks **disk**, `status._stale_count` reads the **files table** — and the full-index path never deleted the row of a file that had left the tree. `_delete_file_entries` already existed and already cascaded correctly; it was only wired into `incremental_index`. The mismatched number was the least of it: deleted files' nodes kept surfacing in dead_code and architecture answers, `_auto_reindex_if_stale` gated on a count a full reindex could never clear so it re-fired forever, and `freshness` answered `"fresh"` for an hour on age alone while `stale_files > 0` — one field contradicting another in the same payload. `_prune_missing_files` runs **before** the dependency passes, so no edge is built onto a node about to be deleted; missing-on-disk is the only criterion, deliberately, because that is scope-independent and a `core` index must not prune what a `full` index wrote; an `OSError` while testing existence counts as present, since a transient stat failure must not delete a file's graph. Reported as `files_pruned` so the deletion is never silent. The contract had already been written down in `test_graph_stale_count_agreement.py::test_a_deleted_file_is_stale` — the *"drops its nodes"* half of it was never implemented.
- B012: reported as "`lang: json` returns `ok: true` for broken JSON". Measured first, and the report's diagnosis was wrong — `lang="json"` already returned a real `JSONDecodeError` and `lang="js"` really ran `node --check`. The defect was worse than reported and sat in the terminal `else`: any unrecognised `lang` answered `ok:true, lang:"none"` with nothing run and no mention of that, so a broken file passed under `JSON`, `Json`, `jsonc`, `javascript`, `node`, `py` — three of which name a language the tool **does** implement, under another spelling. The registered schema documented 4 languages while the code branched on 9, so the vocabulary was unlearnable except from source. Now: alias normalisation, an `UNSUPPORTED_LANG` refusal carrying `supported_langs`, and a `checked` boolean on every answer so `ok:true` is never ambiguous about whether anything ran — `auto` on an unknown extension still passes, because `write_fix` validates every write and must not fail a `.txt`, but with `checked:false`. The json branch additionally rejects two RFC-8259 violations Python's `json` accepts by default: `NaN`/`Infinity` literals, and duplicate keys (silently last-wins, i.e. data discarded).
- B013: `dependency_edges: 0` on a repo with 426 callables, so `module_deps` / `imports` / `imported_by` and every cycle query came back empty. The report blamed `require()`; measurement found **two** independent gaps, and fixing the named one alone would have left every ESM project at zero with the symptom intact. (a) `require()` is a `call_expression` and never reached `_emit_import`, so CommonJS produced no import node at all. (b) ESM *did* emit an import node, but path-shaped — `./lib/util.js.helper`, whose dotted prefixes start with `/` and can never equal the module key `lib.util` the indexer builds from `_dotted_from_path`. `_module_key()` now resolves relative specifiers against the importing file's directory at **extraction** time, which is the only place it can be done: the indexer no longer holds that directory when it walks import nodes. A bare package specifier (`fs`, `express`) is left unresolved on purpose rather than collided with a same-named local file, and a test pins that restraint. Measured on the reported repo: dependency_edges **0 → 46**, with `unresolved_imports: 38` correctly accounting for the bare packages.
- B014: `cbm_dead_code`'s `file_filter` was accepted and discarded. The decisive measurement was not the reported one — a **bogus** glob (`no/such/dir/**/*.js`) returned the same 207 candidates as no glob, which proves the argument is inert rather than merely broad. `_cbm_dead_code_dispatch` resolved the glob and then early-returned into `_cbm_dead_code_ast_p0`, which had no parameter to receive it, and neither did `query.dead_code_candidates`; separately, the glob was hard-filtered with `path.endswith(".py")`, so a `*.js` pattern matched zero even on the Python path. `rel_files` is now threaded end to end, where an empty **set** means "matched nothing" and `None` means "no filter"; the `.py` hard-filter moved behind the language check where it belongs. The response echoes `file_filter`, `file_filter_applied` and `files_matched`, so a glob that matched nothing reads as `files_matched: 0` instead of looking like a full scan. Measured: 208 (no filter) / 131 with `files_matched: 28` / 0 with `files_matched: 0`. The user's underlying need was the real point — with `scope` limited to `full|core` there had been no way to exclude a large data directory, which is what made the tool unusable on their repo.
- B015: the same tool advertised "Ruff-powered ... Vulture supplements" while silently handing a non-Python repo `engine: "ast-p0-v1"` — a different analysis with different semantics wearing the other one's description. Falling back is legitimate; not saying so is the defect, and it also concealed that on a JS repo the `bug_risk` / `perf` / `complexity` / `code_smell` / `tech_debt` / `security` categories are Ruff-only and therefore empty **by construction**, not because the repo is clean. Every answer now carries `engine`, `engine_reason` and `language_detected`. `_detect_majority_language` had been returning only `"python"`/`"other"` — adequate while it merely gated the engine choice, but as a reported field it threw away what it had just counted, so it now answers `"javascript"` when it counted JS/TS files.
- Deferred explicitly by Anh, and recorded as a gap rather than a fix: JS/TS equivalents for the Ruff-only categories ("1 số tool python sẽ không bắt được, nâng cấp sau"). An empty `bug_risk` on a JS repo is not good news, and MAINTENANCE_DOCTOR.md now says so in the triage table.
- 39 tests added across 4 new files, every one written before its fix and confirmed failing first. Two harness requirements recorded for anything touching the graph: `ORCHESTRATOR_PARALLEL_INDEX=off` (the `_snapshot_files` ProcessPool is not spawn-safe), and `CBM_EXTRACT_JS=1` + `CBM_GRAPH_ENABLED=1` per test — a JS graph test missing either one passes vacuously.
- Baseline: **2517 passed, 0 failed, 4 skipped, 1 xfailed, 165 subtests passed in 388s** with `--basetemp` on `C:` (2478 before these 39). README.md baseline updated (2444/231 files → 2517/239 files).


## 2026-08-20 — campaign-1608 audit: eight defects fixed, 73 tests added

- Audited a prior weak-model campaign against the live tree rather than its report. Structure was sound; eight real defects were found, all fixed and registered as B002-B009 in KNOWN_BUGS.md. B008 came from verifying B006 live after the restart rather than from the report — the same audit standard turned on this campaign's own output.
- Added MAINTENANCE_DOCTOR.md: symptom-first triage for the next CA, built on the observation that the first plausible cause was wrong in every single case. Each entry gives the symptom as it appears, the cause that was assumed, the cause that was real, and the test that pins it.
- B002/A54: a stale `pytest-current` symlink aborted the entire suite at COLLECTION with WinError 5. Windows can leave an orphaned symlink readable-but-not-stat-able, and `Path.exists()` propagates EACCES, which kills pytest's own temp-dir garbage collector. conftest.py now replaces `cleanup_dead_symlinks` with a per-entry-tolerant version — not a blanket try/except, which would leak every dead link behind the first unreadable one.
- B003: the WinError 5 above had previously been misread as OneDrive syncing %TEMP%, which produced a `--basetemp` on `D:`. `D:` is a HDD; the suite's temp I/O saturated the spindle until unrelated folders would not open in Explorer. %LOCALAPPDATA% is never OneDrive-redirected. Removed the `--basetemp=tests\tmp_fresh` recommendation from README.md; full suite 699s -> 352s.
- B004: `test_append_jsonl_parallel_process_thread_keeps_all_lines` was flaky only in the full suite because its `join(timeout=10)` was tighter than the module's own documented `LOCK_TIMEOUT_SECONDS = 15` plus ~6s of fsync per worker (125ms measured x 50 appends). The deadline is now derived from the module constant; the liveness assertion stays.
- B005: `_reindex_from_disk` was deleting live CA sessions' `CA_SESSION_BOOTSTRAP.md`. `PRESERVED_CACHE_FILES` compared whole relative paths and was written before session artifacts moved to `sessions/<label>-<digest>/`; `WORKFLOW_STATE.json` survived only by accident. Preservation now matches the final name, the basename at any depth, and the in-flight `.<name>.<random>.tmp` shape, without widening to cover the A02/A30 write ledger.
- B006: git_status/git_stage/git_commit exceeded the ~63k transport ceiling and arrived truncated, and `expected_staged_hash="auto"` was refused as GIT_STATE_STALE. `records` is now capped with the cap reported (0 = uncapped, the default); counts/state_hash/staged_hash are computed over every record and moved ahead of `records`, so a capped read and a full read are interchangeable; `"auto"` is an explicit opt-out of the staleness check only; a missing hash says EXPECTED_STAGED_HASH_REQUIRED and carries the retry hash.
- B007/CASE-2008: authorization was never the missing part — the caller was authorised, and a token-gated tool with no confirmation gate is what caused the loss. Added a shared whitelist-only destructive gate to run_project_test_script AND run_project_command (a separate entry point to the same filesystem): dry_run preview, `confirm_destructive=<count>` with stale counts refused, DESTRUCTIVE_SCRIPT_FOOTGUN non-confirmable, four-interpreter pattern union, no self-truncation of a destructive run's output, and a failed backup refusing the run. Measured against 34 real call sites: 0 flagged.
- The mutation token now carries a two-sentence mini rule (whitelist-only deletion, fail loud) at all four surfaces a CA can meet it — both handouts and both refusals — bounded to exactly four call sites and counted by a test.
- B008: `git_commit` over HTTP refused a missing `expected_staged_hash` as `MISSING_REQUIRED_FIELD` at the schema layer, which cannot carry `current_staged_hash` because it has no git state — so B006's own stated recovery ("the corrected retry needs no second call") was unreachable from every real caller. All 11 of B006's tests called in-process, below the validator. Removed the field from the registry `required` list; it stays declared and stays enforced, by the layer that holds the data. When two layers can refuse the same call, the one that runs first must not be the one with less information.
- B009: `query_sqlite` reported a busy writer as `QUERY_SQLITE_ERROR: database is locked` with `retryable` defaulting to false, so contention was indistinguishable from a bad request and the one correct action — wait and resend — looked wrong. The connection was not missing a busy timeout, as first assumed: `connect(timeout=10)` already installs one. `sqlite3.OperationalError` is now split out — lock/busy text answers `SQLITE_DATABASE_LOCKED` with `retryable:true`, `retry_after_seconds` and `busy_timeout_ms`, while a SQL typo stays a hard error — and the wait is a named 20s constant instead of the stdlib default. An explicit `PRAGMA busy_timeout` added alongside it was removed after a mutant that deleted the line survived every test: the fix reviewing itself.
- TA-1/TA-6 (`write_fix` on a large file client-times-out and the caller cannot tell whether it landed): investigated as a write-path problem, closed as a documentation one. Measured against the live daemon on a 10MB file with a deliberate 4s client timeout: the client raised `TimeoutError` at 4025ms, `/api/write_status?project_path=..&file_path=..` answered `commit_state: in_flight` / `safe_to_retry: false` at t+4573ms, and `committed` at t+53961ms with `bytes_written: 10337814` and `validation_ok: true`. The ledger opens before the tool runs, so the recovery path was complete the whole time — but `write_status`, `operation_id` and `write_status_url` appeared in **zero** CA-facing documents, which is why the item kept being re-filed as unfixed. Now documented in CORE_RULE.txt and SLIM_RULE.txt (via `write_fix`, as their SOT contract requires), README.md, and a MAINTENANCE_DOCTOR.md section. The async early-return refactor the item originally asked for was not done: it would restructure the write path of a self-hosting production daemon to add a signal that already exists. Stage timings taken while measuring, so the next CA does not re-derive them: on a 9.9MB file `write_fix` took 70.6s normally and 27.5s with `skip_symbol_check=true`, so the post-write symbol check owns the wall clock — `backup_override` saved ~0.6s, and `backup_project` already skips when today's backup exists.
- B010 (MCP answered `UNSUPPORTED_FIELD` for fields the daemon accepts): found while verifying the TA-5 self-heal after the restart to generation `4c69c7c10f4b`. `git_status` with `max_records` returned `ok:true` over HTTP and `UNSUPPORTED_FIELD` over MCP, with `accepted_fields` that predated commit `ba88645`. `dispatch_tool_call(transport="mcp")` screened payloads with `_schema_for_tool()`, which reads the registry of whichever process runs the gate — for MCP that is the stdio bridge, a separate long-lived process holding whatever schema it imported at launch. The give-away: a call the gate *did* pass came back carrying `records_total`, a field only the new code emits, so the handler was new and only the gate was old. TA-5 did not cause this; by replacing a fatal generation mismatch with a re-baseline it made the bridge proxy to a daemon whose schema it no longer shares, which turned a latent gap into a visible one. The screen's stated justification (sharing the duplicate-retry ledger) was already false — `_bridge_dedup` covers every `_DETERMINISTIC_TOOLBODY_ERRORS` verdict. Screen deleted; the daemon's registry decides. 4 new tests, both mutants killed. Two existing tests were re-pointed from the decision site to the outcome, and `test_duplicate_retry_guard.py` turned out to have had **no HTTP mock at all** — it was POSTing to the live daemon on 8083 and asserting against that process's ledger, which is why it passed alone and failed in a group.
- 77 tests added, every one mutation-verified by reverting the fix at runtime and confirming failure. Two harness traps recorded: a copied test file resolves `_ROOT` to the scratch dir and fails for the wrong reason, and `-p` plugins load before conftest, so a revert must go in a `pytest_collection` hook.
- Baseline after the campaign: 2474 passed, 0 failed, 4 skipped, 1 xfailed, 165 subtests passed in 327.46s, with `--basetemp` on `C:`. README.md corrected: 7 mojibake lines, 3 references to non-existent docs (TEST_HARNESS.md, EXECUTION_TRACKER.md, SOT_MAPPING.md), version marker R42 -> R102, and the stale 385-test baseline.

# ToolA Ledger Sweep — Design (Final)

Purpose: keep ToolA's two history ledgers — `durable_audit.db` (table `durable_audit_outbox`) and `sessions.db` (table `events`) — under a combined cap of **1 GB**, deleting history oldest-first, without ever touching live state, without endangering the daemon, and with a written receipt for every run. User order 2026-11-10 13:22 +07; design converged by museB campaign `brainstorm-20261110-1322` (review wave 5 of 5 — the handover checkpoint wave — closed unanimous APPROVE-with-nits; the wave's nits are folded into this final text; §12 re-measured fresh at filing, 2026-11-10 14:27:54 +07). This document is the design; execution (any deletion, the conversion window, enabling the schedule) happens only after the user's approval of the first-cut list in §12.

Paths: ledgers live in `D:\0. TRIEN\1. DATA\DATA\5. VIBE APP\1. APP\8. ToolA\project-orchestrator\.orchestrator_cache\`; receipts and alarms go to `D:\0. TRIEN\1. DATA\DATA\5. VIBE APP\1. APP\41. CLAUDELTNAI\ledger_sweep\receipts\` (the intro path — §8's fields live there).

## 1. The cap, defined

- **Cap metric:** `(durable_audit.db + durable_audit.db-wal) + (sessions.db + sessions.db-wal)` ≤ **1,000,000,000 B** (decimal GB — the user's "1 GB"). The `-shm` files are excluded from the metric: they are transient shared-memory images, not stored history (durable shm measured 491,520 B, SOT C-2; the sessions shm was unmeasured in the SOT — the filing-time measurement in §12 closes that gap, and every run's receipt records both shm sizes informationally).
- **Trigger thresholds (same metric, peak-based — §4):** the sweep projects the **peak until the next run**, P + I, where P is the metric measured in-run and I is the one-day growth allowance (§10 derives I = 180,000,000 B from the largest measured one-day growth). Trim fires when P + I > 950,000,000 B and trims until P + I ≤ 850,000,000 B, with P re-measured on this same metric inside the trim loop (§5) — so for any day whose growth stays within I, the peak never exceeds 950,000,000 B (§10 states the entailment conditionally, with its robustness envelope).
- Measured now (2026-11-10 13:1x, on the cap metric): durable file 1,205,116,928 B + WAL 237,019,512 B; sessions file 1,055,690,752 B + WAL 19,520,592 B (sizes SOT C-2, C-6); combined on the metric = **2,517,347,784 B ≈ 2.52 GB**. (The SOT's own combined figure, 2,517,839,304 B, additionally includes the durable shm; the difference is exactly 491,520 B.) Of the file bytes, ~842 MB is already-dead freelist (durable 81,470 pages × 4096 = 333,701,120 B; sessions 124,047 × 4096 = 508,096,512 B; SOT C-2, C-6) — reclaimable by compaction without deleting a single live row. Sessions page_size 4096 is proven, not assumed: 257,737 pages × 4096 = 1,055,690,752 B reproduces the measured file size to the byte (campaign fact-check FC-2), and §12 re-reads the pragma directly at filing.

## 2. Baseline — what already exists (the corrected model)

This design adds a sweep to a system that already prunes; it does not greenfield one.

- The daemon already deletes old applied outbox rows at every writer start: `prune_applied_older_than()` (audit_writer.py:1291-1382) uses the positive predicate `state='applied' AND created_at <= cutoff` (audit_writer.py:1306-1310, and again at audit_writer.py:1364-1368), in 2,000-row batches (audit_writer.py:123), via the index `ix_durable_audit_outbox_state_created` (state, created_at, audit_id) (audit_writer.py:245-246). Its window comes from env `ORCHESTRATOR_DURABLE_AUDIT_RETENTION_DAYS`, default **14 days** (audit_writer.py:121-123), read live at each call with a safe fallback (audit_writer.py:126-142). It runs **once per writer start only** (`_prune_applied_on_start`, audit_writer.py:1384-1398) and **deliberately never VACUUMs** (audit_writer.py:1322-1324). Its return shape already carries receipt-grade fields — `ok, retention_days, cutoff_epoch, eligible, deleted, batches, dry_run` (audit_writer.py:1348-1356) — and it has a **dry_run mode explicitly built for destructive-gate review** (audit_writer.py:1326-1327).
- `state='applied'` certifies the record was **mirrored into the session store**: the sink `_persist_durable_session_event` (orchestrator_server.py:1043-1045) is invoked at audit_writer.py:1241 before `_mark_applied` (audit_writer.py:1272). The prune docstring states applied rows have "already been mirrored into the session store and nothing ever reads it back, so it is pure history" (audit_writer.py:1302-1304). In particular, `write_status` recovery never reads the outbox — it reads the in-memory `_WRITE_LEDGER` plus sessions.db `write_operations` (orchestrator_server.py:19352-19355, orchestrator_server.py:3078, orchestrator_server.py:3034, orchestrator_server.py:3045, orchestrator_server.py:3083). The outbox state column is constrained to `('pending','applied')` only (audit_writer.py:233-234) — lease and retry are *fields* on pending rows (`lease_owner`, `lease_until`, `next_attempt_at`), not states. The outbox `created_at` column is `REAL NOT NULL` (audit_writer.py:235): the outbox NULL census is therefore structurally zero and §5's in-predicate `typeof` term is exact against this schema — the type/NULL risk lives on the events side (nullable TEXT, store.py:1300).
- The sessions store prunes **sessions** older than **10 days** — a window the code records as the user's own choice (store.py:104-106) — once after boot, and the prune **cascades into `events`, `pending_audits`, `task_checkpoints`, `write_operations`, `read_tokens`** (store.py:1598-1685; cascade at store.py:1625-1649, store.py:1661-1664). **The sweep must never invoke `prune_sessions_older_than`** (§4, K-1). A `vacuum_sessions_db()` exists (store.py:1688-1706, EXCLUSIVE lock) with **no production caller**. `auto_vacuum` appears 0 times in the repository — both databases are mode NONE today (a repo-text fact; §12 reads the pragma directly at filing).
- The store's retention code already implements the type discipline this design reuses: `_retention_cutoffs` builds `(iso_text, epoch_float)` cutoffs in one helper and never compares across storage classes (store.py:1576-1595; rationale at store.py:1590-1595), because a REAL < TEXT comparison in SQLite silently matches **every** row (the same trap documented at audit_writer.py:1312-1315).
- `events` has **no index on created_at** (store.py:1363-1385); its primary key is `id INTEGER PRIMARY KEY AUTOINCREMENT` (store.py:1289), so id order is insertion order; `created_at` is TEXT and **nullable** (store.py:1300). The store deletes events only by session cascade, never by created_at. Deleting events by created_at via SQL therefore pays a full scan (measured ~85 s for a bare age count under load, SOT C-7) — §5 avoids it by comparing in the script, per batch.
- Restart interplay (load-bearing): **any** daemon restart fires both boot prunes above. A restart inside the conversion window (§7) therefore changes live-state counts by the boot prunes' own action — receipts must attribute those deltas to the restart, never to the sweep (§7 step 9).
- Daemon write budget: the audit writer runs `busy_timeout` 1,000 ms × 4 attempts plus backoff sleeps (audit_writer.py:81-99); the repo's own F17 measurement (tests/test_audit_writer_busy_budget.py:5-12, measured 2026-09-27) shows a 2,000-row DELETE on this spinning disk can outlast that budget and fail a concurrent `stage()`, parking the payload on a replay spool. The daemon maintains that spool as a file, `durable_audit_spool.jsonl`, beside the database, with in-process counters (`spool_parked_total`, `spool_depth`, audit_writer.py:365-370) — the sweep watches the file (§5, §8, §9.14). The sessions prune uses `busy_timeout = 30000` (store.py:1602).
- Growth (bounded, not unbounded): the 14-day / 10-day retentions bound long-run size; the measured ≈170 MB/day is a recent **fill rate** (SOT C-9 as qualified in review). Per-table split (one base, the 13:1x second measure): outbox inflow = last-48 h remainder 121,948 rows ÷ 2 = **60,974 rows/day ≈ 60.7 MB/day** at ≈996 B/row; events = 650,790 rows over the measured span 2026-10-30T23:48:29 → 2026-11-10T13:16:44 ≈ 10.56 days ≈ **62,000 rows/day ≈ 52 MB/day** at ≈842 B/row (span-derived — a floor estimate). Total content inflow ≈ **113 MB/day**. The two rates measure different things and neither contradicts the other: ≈113 MB/day is the two history tables' *content* inflow; ≈170 MB/day is growth of the *metric itself* (file bytes — it additionally includes WAL churn, freelist churn, and live-state write volume). §10's allowance I is derived from the metric rate, the quantity the cap actually constrains. Byte-per-row figures assume uniform row size — estimates, labeled as such wherever used; §7's window gates retire the estimate risk at execution (§7 steps 2 and 6b).

## 3. Architecture — executor

**Chosen: (b) a Windows Scheduled Task + one standalone script, plus a read-only VM-side freshness checker.** Rejected: (a) an external cron agent driving the sweep through ToolA — every ToolA call itself writes ledger rows (self-pollution), and the lane is serial with a ~300 s timeout envelope, wrong shape for a 45-minute job; (c) in-daemon self-maintenance — the right long-term home, filed as the separated follow-up in Annex B with an evidence-based promotion trigger (§13), not smuggled into this design.

- **Task:** name `ToolA_LedgerSweep`; daily 03:40 local; **run whether the user is logged on or not** (a stored credential is the user's to supply at task creation — the design requires the setting, not the credential); **wake the computer to run** enabled; "run missed start as soon as possible" ON (a missed run may therefore start under morning interactive load — R-YIELD, §5, is the bound on the harm, and the receipt records the actual start time); "do not start a new instance" if still running; execution time limit 60 minutes. 03:40 is chosen for margin, not quiet: the entailed peak (≤ 950,000,000 B, §10) leaves ≥ 50,000,000 B of margin to the cap for any day whose growth stays within the allowance I — an all-night museroom storm day at the largest measured growth rate is absorbed inside I, and a larger day cannot breach silently (ALARM-CAP-AFTER-RUN on the measured post-run total, §9.2; the floors are never sacrificed to chase the cap, §9.3); no SOT evidence establishes any quiet hour (background traffic runs around the clock — SOT C-9's traffic classes, C-16's continuous writing).
- **Script:** one file, `ledger_sweep.py`, in the project tree (versioned with the repo), Python stdlib `sqlite3` only, **zero ToolA calls**. It opens both databases directly, runs §4–§6 in the order §5 specifies, writes the receipt (§8) on **every** exit path including aborts, writes an ALARM file on any non-clean exit (§9.13), and sets a non-zero exit code on any alarm condition.
- **Checker:** a daily read-only VM-side check (~08:00) that lists the receipts directory via the wrapper (`get_file_tree`, depth-bounded) and reports to the parent **only** when (i) the newest receipt is older than 26 h, (ii) an `ALARM-*` file appeared, or (iii) the newest receipt's status is not OK — OK-FLAGGED counts as not-OK for this trigger; for OK-FLAGGED specifically, the checker compares against the previous receipt and surfaces on first appearance and on any change in the flagged counts (an unchanged standing flag is logged, not re-reported, so a permanent flag cannot train anyone to ignore the trigger; for non-count flag causes — a step-8 disagreement, an unparseable marker — the flagged count is 1 while the cause is present and 0 when absent, so appearance or disappearance is the delta), or (iv) a fallback receipt or ALARM file exists beside the script (§8's fallback location) that the main folder does not show, or (v) a window receipt (§7) whose recorded end state contradicts its exit's row in §7's exit matrix. The checker surfaces each ALARM file once — it tracks surfaced filenames in its own state file; a still-present file is not re-reported, and ALARM files persist on disk until the human deletes them after handling (§8). Cost, stated honestly: a handful of ledger rows per day — the mechanism is paid for in the same currency it saves, at ≈0.005% of daily inflow. The script also self-checks: if the previous receipt is older than 36 h at run start, it writes an alarm file before proceeding. Degradation, stated plainly: if the VM checker itself dies, detection of a dead task waits for a human to open the receipts folder — receipts are durable files, so detection is delayed, never lost; if the task dies *and* the VM is down, surfacing waits for either to return (§11).

## 4. Retention rules

- **R-RET-OUTBOX (nightly, unconditional):** delete `durable_audit_outbox` rows where `state='applied' AND created_at <= now_epoch − 48h`, chunked per §5. The 48 h floor is kept — but on its defensible grounds, not the seed's: (i) incident symmetry — an unapplied row older than 48 h is an alarm (§9.1), so history younger than the alarm threshold is exactly the window an incident review needs; (ii) hot-path zero-risk — applied rows are mirrored history (§2), so the cut costs no live capability; (iii) sizing — 48 h of outbox content ≈ 121 MB keeps the §10 trace comfortably entailed. **No cap-override deepening:** the script never deletes younger than an approved floor; if floors bind before the cap target is reached, it escalates (§9.3, ALARM-FLOOR-CAP) instead of silently overriding the floor the user approved.
  - **Forensic trade-off, disclosed:** design history in this repo designates outbox duration data (read mode=ro) as a latency-percentile source (docs/PLAN_TOOLA_1210_FINAL.md:1048), and incident reconstructions in the repo's own records span multiple days. Cutting at 48 h spends that read-back. The user's standing ruling (2026-10-08: the audit DB is never used for tracing; traces live in session files) accepts cutting audit history; the concrete cost — multi-day latency forensics from the outbox — is named here and in the approval ask so the approval covers it knowingly. The 14-day boot prune already bounds this history today; 48 h is a tightening, not a new kind of loss.
- **R-RET-EVENTS (three parts):**
  1. **Weekly ceiling (Sunday run):** delete `events` older than 10 days (`created_at` before `now_local − 10 days`), per-batch per §5. This mirrors the horizon the user already chose for sessions (store.py:104-106). Between Sundays the ceiling does not run, so events content sawtooths — §10 walks the sawtooth honestly; the ceiling is the absolute backstop, not the weekly bound.
  2. **Cap trim (any run):** the sweep measures P (the §1 metric, in-run, after the outbox cut, the ceiling if Sunday, incremental vacuum, and the checkpoint — §5's order) and projects the peak until the next run as **P + I** (I = 180,000,000 B, §10). If P + I > 950,000,000 B, delete oldest events (§5's per-batch trim) until P + I ≤ 850,000,000 B — **never** deleting an event with `created_at >= now_local − 7 days` (absolute floor).
  3. **Escalation:** if the 7-day floor binds before the target is reached → stop trimming, write ALARM-FLOOR-CAP, escalate. The floor is never broken by the script.
  - Disclosure: under cap pressure the trim can delete events aged 7–10 days belonging to still-live sessions, and the Sunday ceiling can likewise delete >10-day events of a session that is still live in a long-running daemon (events are history rows; live state is the `sessions` table, untouched — §2). Both costs are named here and in the approval ask.
- **Never:** the sweep never invokes `prune_sessions_older_than`, never names a live-state table (`sessions`, `read_tokens`, `write_operations`, `task_checkpoints`, `pending_audits`) in any DELETE, and never deletes an outbox row whose state is not `'applied'` (K-1, K-2).

## 5. Deletion mechanics (under live load)

**Run order (fixed):** (1) type census per database — abort conditions below; (2) spool file size, before; (3) outbox chunks; (4) events ceiling (Sunday runs only); (5) `incremental_vacuum` (§6); (6) checkpoint (§6); (7) measure P **on the §1 metric** (file bytes = `page_count × page_size` per database, plus measured WAL bytes); trim if P + I > 950,000,000 B, re-measuring P on the same metric after each batch (§5 trim paragraph); (8) if the trim ran: the closing `incremental_vacuum` of §6 (the full loop, not a single call) + a PASSIVE checkpoint, then a final filesystem measurement of P for the receipt — it must agree with the page_count-derived P within 1,000,000 B per database after accounting for the receipt's own WAL before/after delta (the check exists to catch a broken estimator, not live-write drift between two measurements seconds apart); a larger disagreement marks the receipt OK-FLAGGED (§8); (9) spool file size, after; (10) live-state counts (informational); (11) receipt.

- **Type guard (load-bearing, two layers):** storage class in SQLite is *per value*, so a one-row probe certifies nothing. Layer 1 — **in-predicate:** every outbox chunk carries `AND typeof(created_at) = 'real'`; every events batch row is read with its `typeof(created_at)` and is deletable only if it is `'text'` (§5 events form). A wrong-class or NULL row is therefore structurally undeletable by the sweep, whatever the cutoffs. Layer 2 — **census:** before the first DELETE of each run, the script counts, per table, the rows whose `created_at` storage class differs from the expected class, and the NULL-`created_at` rows (outbox: one indexed count; events: a dedicated full scan, mandated as the only form — a count riding the first batch pass would census at most 2,000 rows and could not deliver this paragraph's abort guarantee — costed at the C-7 scan class, once per run, never per chunk, and completed before the first DELETE of the run for both tables). Receipt fields carry both counts per table. **Any non-NULL nonconforming row aborts the run before any delete** (ALARM-TYPEOF, §9.9). Two adjacent cases are pinned, not left to the implementer: (a) a text-class events row whose `created_at` does not parse as an ISO timestamp is ineligible in both events passes (never deleted), is counted in every receipt as `events_unparseable_created_at`, and a count > 0 marks the receipt OK-FLAGGED (§8) so the checker surfaces it — it is not a class mismatch and does not fire ALARM-TYPEOF; (b) in the ceiling pass a wrong-class row is simply ineligible and stops the batch's eligible prefix like any ineligible row (the census has already aborted the run if any non-NULL wrong-class row exists, so in a running pass this case is unreachable). NULL shielding, stated beside the ceiling's approximation below: a NULL-`created_at` row stops every ceiling pass at its id, permanently shielding older events behind it from the ceiling alone; the cap trim examines every row in every batch and is unaffected — the ceiling is age hygiene, the trim is the cap's enforcement. NULL-`created_at` rows are never deletable by any age predicate — they are counted in every receipt so their population is visible; growth of the NULL population is a data-quality signal for the parent, not a sweep alarm. Offset-aware values, pinned: an events `created_at` carrying a UTC offset suffix in any form, including `Z`, is normalized to naive local time by its offset before any comparison and counted in the receipt as `events_offset_bearing_created_at`; a string that fails parsing even after normalization falls under case (a). (The store's writer path emits naive local text — store.py:2542 — so offset-bearing rows are foreign, but they are normalized, not abandoned.)
- **Cutoff discipline:** cutoff values are built by one helper returning the `(iso_text, epoch_float)` pair — the store's own pattern (store.py:1590-1595) — and are never compared across storage classes (audit_writer.py:1312-1315). Events comparisons happen **in the script** (parse the ISO text to a datetime in Python), never as cross-class SQL comparisons. Naive-local ISO cutoffs inherit the store's own convention; this locale has no DST, and a system clock change shifts an events cutoff by the change amount, bounded by the 7-day floor.
- **Outbox chunks:** `DELETE FROM durable_audit_outbox WHERE audit_id IN (SELECT audit_id FROM durable_audit_outbox WHERE state = 'applied' AND created_at <= ? AND typeof(created_at) = 'real' ORDER BY created_at LIMIT 2000)` with the cutoff bound as a float; one transaction per chunk. (The `typeof` term filters inside the index-driven eligible range — the range is exactly the cut set, so the filter's cost is bounded by the cut itself.)
- **Events ceiling (Sunday):** batches of 2,000 rows read as `SELECT id, created_at, typeof(created_at) FROM events WHERE id > ? ORDER BY id LIMIT 2000`, starting from the smallest id. Per row, the script parses `created_at` and compares against the ceiling cutoff. It deletes, by explicit id list (`DELETE FROM events WHERE id IN (…)`), the longest eligible **prefix** of the batch (eligible = text class AND older than the cutoff) and stops the ceiling pass at the first ineligible row. Stated approximation: id order is insertion order (store.py:1289), so age is monotone in id up to replay/backfill skew; a young row shields any older stragglers behind it until the next Sunday — under-deletion, the safe direction, bounded by the trim below.
- **Events trim:** batch reads as above, continuing from where the ceiling stopped (or from the smallest id). Unlike the ceiling, the trim examines **every** row in the batch: a row is deletable iff it is text class AND its parsed `created_at` is **older than the 7-day floor datetime**. Deletions are by explicit id list per batch. After each batch — and after one `incremental_vacuum(4096)` pass on sessions.db, which starts converting the just-freed pages into file shrinkage — the script re-measures P **on the §1 metric**: Σ over both databases of `page_count × page_size` (the current file size; freelist pages are inside it, which is exactly why the metric, not a content formula, governs the loop) + measured WAL bytes; the loop stops when P + I ≤ 850,000,000 B. If a full batch yields zero deletable rows while the target is unreached → ALARM-FLOOR-CAP, stop. The receipt's **effective cutoff for a trim run** = the `created_at` of the last deleted row, with rows deleted and the floor value.
- **Yield (R-YIELD):** 2,000 rows per transaction everywhere (the codebase's own prune quantum, audit_writer.py:123); the sweep connection uses `busy_timeout = 30000` (the sessions prune's own precedent, store.py:1602 — this is *wait* time to acquire, not lock-hold time); **time waited inside `busy_timeout` counts toward the cumulative contention budget**; a failed chunk retries after 2 s, then 5 s; **3 consecutive chunk failures abort that database's phase**; cumulative contention waits over 5 minutes abort the phase; per-database wall budget 20 minutes; whole-run cap 45 minutes; 250 ms pause between chunks. Honest bound: chunk lock-hold (~1 s order per the F17 measurement) can still occasionally park a daemon payload on its replay spool — the risk is bounded, and now actually watched: the receipt records spool file size before/after (§8), and growth across a deleting run fires ALARM-SPOOL (§9.14). Annex B is the structural fix if aborts recur.
- **Idempotence:** every predicate is time-based, so a crashed or aborted run leaves a correct partial state and the next run resumes from the same predicates. Partial progress is always receipted (§8).

## 6. Compaction (per run) and WAL handling

- **Checkpoint:** `PRAGMA wal_checkpoint(PASSIVE)` first — PASSIVE never blocks writers. Only if the WAL still exceeds 16 MB afterwards, one `wal_checkpoint(TRUNCATE)` attempt; a busy result is logged in the receipt, never retried in a loop (TRUNCATE is writer-blocking and can return busy=1 — https://sqlite.org/c3ref/wal_checkpoint_v2.html and https://www.sqlite.org/wal.html#ckpt, via the sqlite.org wal_checkpoint documentation). Today's durable WAL (237,019,512 B ≈ 57,900 pages against a 1,000-page autocheckpoint default) signals checkpoint starvation by long-lived readers — the window (§7) is where it is reset, not nightly force. Note the WAL enters P as *measured bytes* (§5 step 7): a persistently pinned WAL is charged to the trim the same night, not assumed away (§10 sensitivity).
- **Incremental vacuum:** after deletions, `PRAGMA incremental_vacuum(4096)` per database, looping until freelist ≤ 2,048 pages or 60 s per database, whichever first. Valid only after the §7 conversion to `auto_vacuum=INCREMENTAL`; before conversion the step self-skips (mode check first — a silent no-op here is a defect this design refuses, §9.10). How the script knows conversion has occurred — per database, from either of two sources: (i) the `conversion-done.json` marker the window writes at §7 step 10 (receipts folder, or the beside-script fallback of §8 — a distinct location, so the two sources do not share one folder's failure), present **and parseable** (it carries the conversion timestamp and each database's post-conversion mode); or (ii) receipt history: any prior receipt recording that database's `auto_vacuum` mode as INCREMENTAL. A run whose receipt history shows INCREMENTAL for a database treats a mode-0 read as ALARM-AV-OFF for that database **even if the marker is missing** — the marker is a convenience, never the sole evidence, so its loss cannot disarm the alarm. An unparseable marker is receipted (status OK-FLAGGED) and source (ii) governs; a run that establishes conversion from source (ii) with the marker missing **or unparseable** rewrites the marker and receipts the repair — the rewrite is conditioned per database on that database's **live** mode reading INCREMENTAL, and the rewritten marker records each database's live mode as read at repair time (a database reading 0 is recorded as 0 and governed by ALARM-AV-OFF, never re-asserted as converted). Only when neither source establishes conversion does the mode check self-skip — the true pre-conversion state.

## 7. The one-time conversion window (bundled into the first execution's approval)

Numbered procedure, executed once, inside the same approval as the first cut (§12):

1. **Dry-run recount** with the daemon's own machinery — the prune's dry_run mode (audit_writer.py:1326-1327) plus the §12 predicates — and compare against the presented first-cut list; drift > 10% → STOP, re-present.
2. **Online snapshot copies:** `VACUUM INTO` per database to timestamped copies in `.orchestrator_cache\backups\`. These are **pre-window snapshot copies — disaster recovery for the window itself, NOT a live rollback**: restoring one after the daemon has restarted would discard live-state writes landed after the copy was taken (restore procedure and its caveat: step 11). Gates, both checked before anything else proceeds: **(disk)** free space on D: ≥ copies (≤1.42 GB at today's sizes) + 2× the largest database file (the VACUUM workspace bound, https://www.sqlite.org/lang_vacuum.html — ≈2.41 GB for durable_audit.db) + margin → **≥ 4 GB free**, re-derived from the measured sizes at window time; **(sanity)** each copy's file size against the SOT content figure for its database (durable ≈871 MB, sessions ≈548 MB) — divergence beyond ±10% → STOP, re-present (the copies are the first exact byte measurement of the campaign; the approval's estimates stand or fall here). The copies run online against the live daemon and may take minutes under load — that is normal and pre-drain, not a stall.
3. **Drain:** poll the daemon health surface until in-flight work is zero (`executor_active_total = 0`, stable across two polls 30 s apart) — never kill mid-call. **Deadline 30 minutes:** if the drain does not complete, the window ABORTS with the daemon untouched and the abort receipted (the repo's own drain pattern caps polling and reports rather than forcing — docs/PLAN_TOOLA_1210_FINAL.md:1038).
4. **Hold-down, then stop:** before stopping, establish how a stopped daemon could come back: the listener supervisor never restarts the daemon (orchestrator/lifecycle/listener_supervisor.py:1, orchestrator/lifecycle/listener_supervisor.py:31 — it supervises the listener's event loop only); the auto-heal monitor triggers only on the hang signature with defer-on-busy (campaign fact-check FC-1); and when both livez and health are down, healing belongs to the daemon task's own **LogonTrigger / RestartOnFailure** (restart_control_service.py:845-846). The window therefore: (i) reads the daemon Scheduled Task's restart-on-failure settings and interval — if the settings cannot be read, the window STOPs: the watch term in (iv) cannot be established without the interval; (ii) the window ticket carries, as a named reversible line, **disabling the daemon's Scheduled Task itself for the window's duration** — both triggers die with the task, and that is the only mechanism that bounds both: RestartOnFailure is interval-driven and could in principle be out-waited, but LogonTrigger is event-driven (it fires on any logon, including during step 5's offline work) and has no interval to out-wait. **If the task cannot be disabled, the window STOPS before any offline write** — no watch substitutes; (iii) `kill_process` on the daemon's named PID (from /health); (iv) hold-down verification: PID still absent after max(60 s, the interval from (i)) — any reappearance → STOP the window, report; (v) daemon absence is **re-verified immediately before step 5's first offline write and again immediately before step 6** — a daemon present at either check aborts the window (the exit follows the exit matrix's absence-abort rows — which of the two checks failed decides the marker disposition — and the abort is receipted).
5. **Offline work, daemon stopped:** snapshot live-state counts (all five live tables + the two history tables); `wal_checkpoint(TRUNCATE)` both databases; run the §12 first-cut deletes offline (outbox predicate; events per §12 — expected 0 rows) with the §5 type census; then per database, sequentially: `PRAGMA auto_vacuum=INCREMENTAL; VACUUM;` and `PRAGMA integrity_check` must return `ok` (https://www.sqlite.org/pragma.html#pragma_auto_vacuum — the mode change takes effect only via VACUUM). No absence check sits inside this phase by design: the disabled task (step 4(ii)) cannot relaunch the daemon, and any foreign process opening these files makes the VACUUM fail rather than share them — the step-4(v) boundary checks plus lock behavior are the in-phase bound.
6. **Offline tripwire:** live-state counts re-read — must equal the step-5 snapshot **exactly** (daemon stopped: any delta here is the sweep's own doing). Mismatch → STOP, do not restart, report.
6b. **Exact-bytes gate:** with the databases vacuumed and checkpoints truncated, measure the combined total on the §1 metric exactly. It must be ≤ 1,000,000,000 B. If it is not, the window does NOT proceed to enable anything: the daemon may be restarted for service (step 9), but the sweep program halts and the exact figure is reported for a new approval (a deeper events cut is a new consent, §4).
7. **Env alignment (separate strikable line item in the window ticket):** set `ORCHESTRATOR_DURABLE_AUDIT_RETENTION_DAYS=2` at Machine scope (so the bat-launched daemon inherits it at next start) so the daemon's own boot prune enforces the same 48 h floor at every restart (defense in depth if the task ever dies silently). The knob is read live with a safe fallback (audit_writer.py:126-142), so this cannot break startup. Verification is step 9's: the boot prune's return/log carries `retention_days` (audit_writer.py:1348-1356) and the post-restart receipt checks it reads 2. If it reads otherwise, the window does not fail on it — the line is defense-in-depth and the daemon is unharmed; the receipt notes the actual value and the discrepancy for the parent. Striking this line leaves the design valid — the scheduled task remains the primary mechanism.
8. **Deferred, not in the window:** a new `ix_events_created_at` index — §5's per-batch form makes it unnecessary for the sweep; adding schema is deferred unless a future forensic need appears.
9. **Restart** via the standard bat path (the restart tool), then verify: new PID, changed generation, /health ok. **Settle-wait:** the post-restart receipt snapshot is taken only after the boot prunes have completed (the sessions prune runs after readiness plus a quiet window — the snapshot waits for its completion signal in the daemon's log/return stream, or a fixed 10-minute settle, whichever first signals completion). The receipt names boot-prune deltas **as restart effects, sourced from the prunes' return values**, never attributed to the sweep. If the settle expires without a completion signal, the snapshot is still taken at 10 minutes and the receipt marks the boot-prune attribution **provisional**.
10. **Success exit — three actions, in this pinned order, each verified before the next:** (1) write the `conversion-done.json` marker (§6; §8's fallback location if the receipts folder is unwritable) and verify it by re-reading and parsing it — the sweep enable does not proceed without a verified marker in a location the script reads. A marker-verification failure does NOT halt action (2): the daemon task's restoration never depends on the marker. The marker is retried once via the fallback location; if it still cannot be verified, the exit is step-10 partial (marker pending) — the sweep is NOT enabled, the receipt's headline is the marker state, and enablement is completed later by re-running whichever of actions (1)–(3) remain unverified, in order, receipted as a step-10 completion record — the completion record is checked against the success row (trigger (v)), names the window record it completes, and a second completion against the same window record is receipted as a duplicate and changes nothing; (2) re-enable the daemon's Scheduled Task (disabled at step 4) and verify its enabled state by query; (3) enable the sweep's Scheduled Task and verify. **Every other exit follows the exit matrix below** — the three actions are never bundled by implication. The window record is opened at step 1 (status `window_in_progress`) and re-written at every step boundary and at the exit, so an abandoned window leaves its last state on disk for the checker (abandonment after step 4(ii) leaves the daemon down — a self-announcing state for a production system — and recovery follows step 11's discipline). A stale `window_in_progress` record is closed by the step-10 completion record or by the human closing the incident, receipted as a window-record closure note. The window receipt follows §8's fallback rule; a window receipt that cannot be written in either location is a headline STOP at the point of failure — the operator does not proceed on an unreceipted window. On EVERY exit the receipt records `daemon_state`, `daemon_task_end_state`, `marker_state`, `sweep_task_state`, `env_state` (not-set / set-unverified / set-verified-2), and each database's post-window `auto_vacuum` mode (§8's per-DB fields apply to the window receipt too — §6 source (ii) can therefore establish conversion per database from the window receipt itself); the end-state fields take their values from the exit matrix's cell vocabulary, and a recorded end state contradicting its exit's matrix row is surfaced by the checker (§3 trigger (v)). ## 8. Receipts

Every run — success, partial, or abort — writes `receipt-YYYYMMDD-HHMMSS.json` plus a human `.md` twin to the receipts folder (intro path). **Fallback:** if the receipts folder is unwritable, the receipt is written beside the script instead and the exit code is non-zero; the checker lists the script's directory as well as the receipts folder (§3 trigger (iv)) and treats a fallback receipt as surfaced; the Task Scheduler's result code is the secondary evidence of the run. Alarm conditions additionally write `ALARM-<NAME>-<ts>.txt/.md`, with the same fallback — beside the script if the records folder is unwritable — and the checker lists both locations for ALARM files too. ALARM files persist until the human deletes them after handling; the checker surfaces each once (§3). Fields: schema_version; run_id; started/finished; host; script_version; status (OK / OK-FLAGGED / PARTIAL / ABORTED / FAILED + abort reason; OK-FLAGGED = the run completed with a standing flag the checker must surface — e.g. unparseable-`created_at` rows present (§5), a step-8 P-measurement disagreement (§5), an unparseable conversion marker (§6)); per database: file bytes before/after, WAL bytes before/after, shm bytes (informational), freelist pages before/after, auto_vacuum mode, rows before/after, rows deleted, **effective cutoff values actually used** (per database; for a trim run, §5's effective-cutoff definition), **type-census counts** (nonconforming-class rows, NULL-created_at rows, unparseable-created_at rows), statement journal (every DELETE's target table + rowcount — the sweep's self-attestation, user-auditable); checkpoint calls with (busy, log, checkpointed) results; incremental_vacuum pages reclaimed; **spool file bytes before/after**; live-state counts (informational nightly; tripwire-compared in the window, §7 step 6); the window receipt additionally carries §7 step 10's end-state fields; alarms fired; free disk after. The first execution's receipt additionally carries the §12 list as presented and the dry-run comparison.

## 9. Alarms (any alarm = receipt + ALARM file + checker surfacing)

1. **ALARM-UNAPPLIED-48H** — any outbox row with state ≠ 'applied' older than 48 h (in practice `pending` rows: check `lease_until` / `next_attempt_at` / `attempt_count` — the stall fields, §2). Never deleted (K-2). This is the condition the whole design treats as "the mirror pipeline is stalled — a human looks".
2. **ALARM-CAP-AFTER-RUN** — post-run combined (metric, measured) > 1,000,000,000 B, or projected peak P + I > 950,000,000 B after the run's trim opportunity (warn tier). Evaluated at run boundaries: an intra-day excursion inside §10's robustness envelope that never reaches the cap fires no alarm by design and is visible in the next receipt's P series.
3. **ALARM-FLOOR-CAP** — retention floors bound before the cap target was reached (§4 escalation).
4. **ALARM-WAL** — WAL > 100 MB at run start (checkpoint starvation signal; with peak accounting a standing WAL also eats margin — §10).
5. **ALARM-CHECKPOINT-BUSY** — checkpoint busy on 2 consecutive runs.
6. **ALARM-CONTENTION** — a sweep phase aborted under R-YIELD; escalates when aborts occur on 2 consecutive runs (and feeds the Annex B promotion trigger, §13 — a distinct counter: this alarm escalates on aborts in 2 *consecutive runs*; §13 counts ≥2 phase-aborts in *any* 30 days; an implementer must not merge them). (Daemon-side spool harm is §9.14, not this alarm.)
7. **ALARM-NO-RECEIPT** — newest receipt older than 26 h (checker) / 36 h (in-script self-check).
8. **ALARM-TRIPWIRE** — live-state count delta across the offline window phase (§7 step 6); the window does not proceed to restart.
9. **ALARM-TYPEOF** — a §5 storage-class census mismatch (run aborted before any delete).
10. **ALARM-AV-OFF** — `auto_vacuum` mode reads 0 (NONE) at run start for **either** database for which conversion is established (§6's two sources) (mode regression).
11. **ALARM-DISK** — free space on D: < 1.5 GB at run start.
12. **ALARM-INTEGRITY** — window `integrity_check` not `ok`.
13. **ALARM-RUN-FAILED** — any run that exits non-clean for a reason not covered above (exception, FAILED/ABORTED status): a failed run writes a fresh receipt by design (§8), so without this alarm its failure would be invisible to the freshness checks — this alarm is what makes failure itself a surfaced event.
14. **ALARM-SPOOL** — the audit replay-spool file (`durable_audit_spool.jsonl`) grew across a run in which the sweep deleted rows, or exceeds 10 MB at run start: the daemon paid for the sweep's contention with parked payloads. Stated limit: the before/after comparison is a net delta — a daemon restart inside the run window replays the spool at writer start and can net a real parking event to ≈0; the daemon's own spool counters (exposed on its health surface) are the possible second source, filed to the Annex B follow-up, not implemented here.
Silent by design (receipt-only, no alarm): zero-row runs, checkpoint busy once, boot-prune deltas after the window restart (named in the receipt), NULL-created_at population counts (receipted, §5).

## 10. Steady-state trace (the rule entails the outcome)

Definitions, all on the §1 metric: P = combined file+WAL bytes measured in-run (§5 step 7 — and the trim loop re-measures P in exactly this form after every batch, §5: the loop never stops on a content estimate). I, the one-day growth allowance, is **derived from the largest measured one-day growth**: the SOT's gross fill rate ≈ 170 MB/day (C-9) is a rate measured on this very metric — file growth, which already includes WAL churn, freelist churn, and live-state write volume (§2) — plus ≈10 MB of headroom → **I = 180,000,000 B**. I is an empirically grounded allowance, **not a construction bound on reality**: nothing in the rule prevents a single day from growing more; what the rule guarantees is the conditional bound below plus a measured backstop (§9.2 fires on the true post-run metric after every run). The WAL itself is not part of the allowance bet: whatever WAL exists at run start is *measured inside P* and charged to that night's trim.

**Rule entailment:** after every run, either P + I ≤ 950,000,000 already (no trim needed) or the trim ran until P + I ≤ 850,000,000 (or escalated). For any day whose growth G satisfies G ≤ I, the combined total at **any instant** therefore satisfies: ≤ (950,000,000 − I) + I = **950,000,000 B < 1,000,000,000 B**, with ≥ 50,000,000 B of margin — AC-1 entailed by the rule for every day inside the allowance. **Robustness envelope, stated honestly:** from the worst no-trim post-run state (P = 770,000,000 B), the cap itself is reached only if one day's growth exceeds 230,000,000 B (≈1.35× the largest measured rate); such a day is not silent — ALARM-CAP-AFTER-RUN (§9.2) fires on that night's measured P, the next run trims, and the floors are never sacrificed to chase the cap (§9.3). The receipts record each day's measured growth (P delta plus deleted bytes), so the first weeks empirically test I; a sustained G > I re-derives I by the same rule (largest measured + headroom) as a design amendment, never a silent edit.

**Week walk (Sunday → Sunday, estimates at §2 rates, on the metric: P includes WAL ≈ 20 MB steady post-window and a freelist residual ≤ 2,048 pages per database ≈ 16.8 MB combined, left by §6's closing loop; walk figures are rounded to whole MB and the sums hold at that precision):** post-Sunday run: events at the ceiling value ≈ 520 MB (10 days × 52), outbox 121 → P ≈ 678, P + I ≈ 858 (no trim). Events grow 52/day: day 1 → P ≈ 730, P + I ≈ 910 (no trim); day 2 → P ≈ 782, P + I ≈ 962 > 950 → trim events to P ≤ 670,000,000 (events ≈ 512 MB ≈ 9.8 days — above the 7-day floor, no conflict); day 3 → ≈ 722 (no trim); day 4 → ≈ 774 → trim to 670 again; day 5 → ≈ 722 (no trim); day 6 → ≈ 774 → trim; Sunday: ceiling resets events to ≈ 520 → P ≈ 678. Steady state: a trim every second day of ≈104 MB ≈ 124,000 events rows (the first, transitional trim — day 2 above — is ≈112 MB, the Sunday sawtooth's catch-up). The *instantaneous* peak is bounded by 950 per the entailment above — the trigger fires on the same metric quantity the trim loop measures, so no content-versus-file gap exists anywhere in the chain. **Floor branch:** the trim target leaves events ≈ 512 MB; the 7-day floor holds 364·g MB at growth multiplier g, so the floor binds when 364·g > 512 → **g ≳ 1.41×** events-inflow growth. The general condition, so the figure re-derives if the fixed terms drift: the floor binds iff the 7-day floor content exceeds the trim target's events allowance = 670,000,000 B − (outbox file term + WAL + freelist residual) — the 1.41× figure holds those terms at their measured values. In the floor regime, post-run P ≈ 158 + 364·g MB, and ALARM-CAP-AFTER-RUN's two clauses (§9.2) fire at different points: its projected-peak clause (P + I > 950,000,000 B) at g ≳ 1.68, its measured clause (P > 1,000,000,000 B) at g ≳ 2.31; between 1.41× and 1.68×, ALARM-FLOOR-CAP alone is the designed outcome — an alarmed escalation, not a silent breach.

**Stall trace (task dies silently):** worst post-run state P = 770 MB (a no-trim night at the trigger boundary). Cap crossing at the gross file-level fill rate ≈170 MB/day (SOT C-9) takes ≈ 1.35 days — the binding figure, since a stalled sweep leaves the files growing at the metric rate; the slower ≈ 2.0-day figure at the 113 MB/day content-inflow rate is a hypothetical bound that assumes the live-state and WAL churn terms stop contributing. ALARM-NO-RECEIPT fires at 26 h — before both crossings (26 h < ≈32 h); if the §7 step-7 env line was approved, every daemon restart additionally bounds the outbox at 48 h, slowing the approach.

**Publisher-stall trace (AC-2's case):** the mirror pipeline stalls; `pending` outbox rows accumulate, some aging past 48 h. The nightly predicate (`state='applied' AND …`, §5) cannot reach them — pending count is **unchanged** by the run, applied rows older than 48 h are deleted as usual, and §9.1's ALARM-UNAPPLIED-48H fires on the aged pending rows. Zero non-applied deletions, zero live-state writes — by construction of the positive predicate (the daemon's own, audit_writer.py:1306-1310).

**Contention trace:** R-YIELD aborts leave predicates idempotent; the next run resumes; a phase abort under R-YIELD fires ALARM-CONTENTION, aborts on 2 consecutive runs escalate it, and phase-aborts count toward the Annex B trigger (§9.6's two distinct counters). Spool growth across any deleting run fires ALARM-SPOOL (§9.14) whether or not the run aborted.

## 11. Failure detection (nothing fails silently — with its one stated degradation)

Script receipts on every exit path (§8); a non-clean exit writes ALARM-RUN-FAILED (§9.13) and the checker surfaces non-OK receipts (OK-FLAGGED included, §3), ALARM files, and staleness (§3); Task Scheduler history is the secondary evidence; the §7 window has a verification or STOP at every numbered step. A run that cannot open a database, finds a typeof mismatch, or sees the tripwire fire **deletes nothing further and says so in its receipt**. The one degradation, stated rather than hidden: executor-death detection runs through the VM checker — if the task dies while the VM is also down, surfacing waits for either to return; the receipts on disk make the detection delayed, not lost.

## BOOTSTRAP (HARD — the pre-core half lives in SLIM)
POST [A:API]/api/call/get_rule_core_text {"agent_id":"<id>"} once per process/session. The WHEN/HOW of that fetch (valid agent_id list, the already_fetched stub, the sha hash-check, the force:true conditions, compaction is NOT a new CA session, conn-refused→STOP vs running-but-hung→RESTART gate) is published in SLIM_RULE, which every CA already has in context BEFORE this fetch — a procedure for fetching this file must not be documented only inside it, and duplicating it here would drift. Core adds only what arrives WITH core: call bootstrap_session once for compact discovery, and for every real user prompt the host calls begin_task(session_id,prompt,agent_id) and preserves its task_epoch/prompt_hash through tool batches and compaction.
BOOTSTRAP PUSH + EPOCH (A37 #0 — this is the definition of "first call"): the FULL answer, the one carrying text, also OPENS a bootstrap epoch for you and returns tool_purposes (one PURPOSE sentence per read tool, built from the live registry, not from this file), tool_purposes_note and bootstrap_epoch. A purpose says what a tool is FOR; the schema is what says how to call it — that split is deliberate, so read the purpose map to decide WHICH tool, and the pushed schema to call it. While the epoch is open, the first call of each read tool carries pushed_schema (see SCHEMA-FIRST). The already_fetched stub also returns bootstrap_epoch, so you can tell an epoch is open WITHOUT asking for text again, and text_omitted / text_omitted_reason say in-band that a missing text is the expected stub shape, not staleness. A later force:true fetch opens a NEW epoch and re-arms every tool — which is another reason force:true is gated to the conditions SLIM names, not a free refresh. The epoch is keyed the same way the rule-core cache is keyed, per agent_id, so two agents never spend each other's first calls; it is NOT keyed per conversation, so a compaction inside one agent does not re-arm anything — exactly like the rule fetch itself.

## TRANSPORT (HARD)
HTTP /api/call/<tool> = canonical for all non-T4. Host task metadata (session_id, task_epoch, and prompt_hash) is transport-only and MUST identify the newest real user task; stale epochs fail loud. MCP is Clau/ClauC-only for T4 page-stateful. Worker CLI (C-suffix) = HTTP ONLY. Discovery: GET /api/tools/names | /api/tools/<tool>/schema (schema shows requires_session/requires_token per tool). fields= is accepted on EVERY tool and drops nothing: an unknown key answers fields_unknown + fields_available, the keys that DO exist per namespace (the top level is keyed "(top)"), so a wrong guess costs no second call and never needs the full payload; dotted fields=result.files keeps one nested branch. 429→read Retry-After, 413→chunk payload.
MCP DISPATCHER (HARD): [A] MCP is ONE stdio host, orchestrator_server.py --mcp → orchestrator/server/mcp_stdio.py (every launch config found on 2026-09-25 — .claude.json, .codex\config.toml — runs it with no env), and it is a thin dispatcher, NOT one named MCP tool per [A] tool. MCP default surface = call_tool + get_rule_core_text + open_session. Those two shortcuts stay first-class because they resolve the agent id from the HOST env, which the daemon cannot see; every other listed tool cost host context on every turn. Reach everything else over HTTP or call_tool(name=<tool>, payload={...}): list_sessions, log_native_event, council_worker_model and council_message_async are daemon tools and call_tool reaches them. Discovery is NOT a daemon tool: GET /api/tools/names and GET /api/tools/<tool>/schema answer it, so call_tool(name='tool_names') answers UNKNOWN_TOOL — and call_tool itself is NOT an [A] catalog tool either, so the daemon has no schema for it. NEVER invent mcp__project-orchestrator__<tool> (e.g. mcp__project-orchestrator__read_file_range) — that name does not exist and fails No such tool available. The surface is a per-LAUNCH fact: ORCHESTRATOR_MCP_FULL_SURFACE=1 keeps every named per-tool wrapper, ORCHESTRATOR_MCP_PROFILE=council adds council_message_async (its lesson injection runs only inside the host) + council_worker_model + the council/mission pack, and a running host keeps the surface it launched with until its client reconnects — a daemon restart does not reload it. So ask tools/list for the host you are actually on, and do not picture a count: the number is not the point and any number written down goes stale. fields= rides inside a call_tool payload and on every named wrapper, so the daemon's "pass fields= next time" size hint is advice an MCP caller can act on. Prefer HTTP /api/call/<tool> when both channels work; MCP call_tool is convenience for Clau/ClauLTN only. From PowerShell, dot-source [A:P]\project-orchestrator\bin\a.ps1 (Call / RFR / WF / WN / Schema / Names) instead of hand-rolling a client: it sends UTF-8 bytes and base64 writes, decodes the answer as UTF-8, and returns a 4xx's structured answer instead of throwing.
MCP AUDIT GAP (HARD, by design -- not a lost write): only a stateful-T4 tool (_mcp_is_stateful_t4_tool) runs INSIDE the MCP host, and --mcp never opens the durable audit writer (_get_durable_audit_writer returns None; the named state is durable_audit_disabled_in_mcp), so an in-process T4 call leaves only its non-durable USAGE_LOG telemetry row and no durable audit row. Every other tool proxies to the daemon over HTTP and IS durably audited there, so a missing durable row for a non-T4 call is a real loss, not this gap.

## READ ROUTING (HARD — measured 2026-08-19, do not re-litigate)
Native is ALLOWED for pure inspection only: grep/glob/`git status`/`git diff`/`git log`/plain file read. Measured on this repo: git_status 1542ms vs native 164ms; search_code 1199ms vs rg 229ms; regex_search HARD-FAILS (REGEX_SEARCH_TIMEOUT, 5s deadline) where rg answers in 229ms; on a 17GB repo rg is 147ms. Inspection mutates nothing, so it owes NO log_native_event — this is a routing choice, not a fallback.
Read-to-EDIT is NOT inspection. write_fix consumes the stable read_token that ONLY read_file_range seeds; a native read before a write returns FILE_CHANGED_OUTSIDE_ORCHESTRATOR. Recovery = read_file_range(force_reseed=true) then retry.
A native grep/rg/glob that says *no such file* -- or returns 0 results on a path that certainly exists -- is a cwd bug, NOT an absence. Do NOT retry with cd and do NOT conclude the string is missing: call search_code(project_path=<absolute>), because [A] resolves by absolute project_path and never by cwd. Same trap in reverse, measured on this repo: grepping a quoted key ("ca_hint_review") misses source that writes out['ca_hint_review'] -- match the bare name, not the quoting you assumed.
Rule of thumb: native to LOOK, [A] to TOUCH, the cbm INDEX to UNDERSTAND. Prefer [A] search_code when you need INDEX semantics (symbol/callable refs, project map, staleness signal) — rg has none of that.
CBM-FIRST on a LARGE repo (this one is): understanding it by bulk-reading source is the single biggest CSLt violation available to a CA. Ask the INDEX first, read ONE bounded range after — and do NOT look for the tool LIST here: your bootstrap's tool_purposes map already names every cbm_* and ocr_* tool with its purpose, from the live registry, so this file deliberately stops restating it (a hand-copied list here is soft data that rots the moment a tool is added). What belongs here is the ORDER, which no registry can tell you, and the two anchors that ORDER pins: is the graph fresh (cbm_graph_status) → what is the module / entrypoint shape (cbm_get_architecture), then coupling and reachability → which exact symbol and line → read_file_range on THAT range only. Before reading a diff, ocr_map names the few files that actually carry the change (git_stage/git_commit already attach ocr_review by default, so this is navigation, not a duplicate review). Before an edit, cbm_what_if / cbm_dsm on those same files give the blast radius, so the edit set comes from the call graph instead of a guess. Two measured traps to READ, not guess: cbm_test_gap is VERDICT-FREE -- pass is ALWAYS false and score ALWAYS null on every path, which means "no verdict was computed", never "coverage failed"; read the response key pass_semantics, rank coverage_ratio / counts / uncovered_files / isolated_uncovered / gaps, and run run_project_test_script for a real pass/fail. And an empty cbm callers list, or a cbm_dead_code "no callers" verdict, means "no RESOLVED reference" ONLY: the graph resolves a call edge through an imported module/alias, so cross-check with search_code(mode='callers'), which DOES see instance receivers (self.fn() / obj.fn()).
NOTHING is locked. git_status in particular stays mandatory: git_commit requires expected_staged_hash and its only source is git_status.

## MODE (HARD)
DEFAULT=T1 read-only (entry mode for genuinely new tasks). EXECUTE splits in TWO tiers, and the trigger buys only the lower one. MUTATE (write/edit/create/test/deploy/restart, T2/T3/T4b/T4c) needs EXACT keyword "tiến hành" (no paraphrase: "thực hiện"/"làm ngay" ≠ trigger) + clear action - and that is ENOUGH. DESTRUCTIVE (delete, mass overwrite, reset/revert/clean, truncate, drop) needs its OWN confirmation EVERY SINGLE TIME, per instance, naming the exact targets: "tiến hành" NEVER authorizes a delete on its own. T1 read + T4a snapshot need no trigger.
EXECUTE STICKY (MUTATE ONLY): "tiến hành <action>" → ACTIVE_EXECUTE_SCOPE=<action>. Sticky scope does NOT cover DESTRUCTIVE: an active scope carries mutation across turns but every delete is a FRESH gate, so a scope obtained once is never a standing licence to delete. Continues through: turns, tool failures, compaction, write→restart→verify pipeline. Terminates only on: DONE_VERIFIED, BLOCKED, ABORTED_BY_USER, REPLACED_BY_USER, SCOPE_AMBIGUITY. Does NOT reset on: turn end, compaction, tool return, progress report, follow-up. Post-compaction: read handoff for exact go-ahead + check newest msg for stop signals → restore scope if unfinished. Details: skill 02_mode_control + references/sticky-execute-compaction.md.
- DESTRUCTIVE 2-TURN RULE (HARD): never list-and-delete in one turn. Turn 1 = LIST the exact targets (full paths, count) and STOP without touching anything - a dry_run preview is the right shape. Turn 2 = delete only after the human approved THAT list. An approval is spent when used: it authorizes that list once, and a target discovered afterwards needs its own turn. The reason is CASE-2008: an agent deleted the wrong files because one turn both decided the target set and acted on it, so nobody ever saw the set.
- WHITELIST, NEVER BLACKLIST (HARD): delete ONLY what is named. Enumerate the targets and pass them explicitly; never express a deletion as "everything except ..." (rd /s, del *, Remove-Item -Recurse, rm -rf on a directory, --exclude patterns). A blacklist deletes whatever the author failed to think of, and its blast radius grows silently as the tree grows; a whitelist can only be wrong about what it says. If the target set is genuinely too large to enumerate, that is the signal to stop and report, not to widen the pattern.

## SCHEMA-FIRST (HARD — TIERED: the tier follows what a wrong call COSTS)
Before EVERY **WRITE** tool call: GET /api/tools/<tool>/schema → use payload_example as the template → send ONLY fields in schema.properties. Write tools keep fetch-every-call ON PURPOSE: a wrong write costs Correctness, and no token saving is worth that, so this tier deliberately accepts the round-trip and does not try to improve L or t.
READ tools are the OTHER tier, because [A] pushes their contract to you instead of charging you a call for it. While your bootstrap epoch is open (see BOOTSTRAP), the FIRST call of each read tool returns pushed_schema — byte-identical to what GET /api/tools/<tool>/schema serves, because one function builds both — plus pushed_schema_note. A later call of that same tool does NOT repeat the push: you already hold it. An ERROR on it DOES re-arm the push and says so with schema_rearmed:true, because an error is the evidence you do not really hold the schema, which is exactly when re-reading it earns its bytes. So: never spend a call fetching a schema that was pushed to you, and never claim you fetched one you did not. A read tool you have not called since bootstrap, whose schema therefore never arrived, still owes the normal fetch.
Either tier prevents the same 90% of CA soft-data errors:
- PowerShell malformed JSON → use payload_example, never hand-write JSON
- git_stage/wrong field (paths[] not file_path) → schema shows array type; R36 alias now maps file_path→paths=[file_path] as fallback
- search_code missing project_path → required=[] shows mandatory fields
- open_session extra file_path → only send schema.properties fields; and mode is the WORKFLOW TIER enum, never an execution verb
- Bash single-quote mangle → use JSON array/file input, not shell concat
- write_fix is FLAT and takes ONE region per call (file_path, start_line, end_line, new_content). There is no edits[] array, so multi-region = several calls, and they MUST go BOTTOM-UP because an earlier top region renumbers every line under it.
On UNSUPPORTED_FIELD/SCHEMA_VIOLATION: read error.accepted_fields + corrected_payload, remove extras, retry once. If accepted_aliases present, apply alias mapping (no escalate). NEVER guess field names; trust schema.
ROOT-CAUSE RULE (truy gốc, không vá ngọn — HARD): when a CA calls a tool wrong, the FIRST question is whether the contract the tool itself publishes (enum / description / rule text) INVITED the wrong call. If it did, NARROW THE CONTRACT — do not add a response field to explain the mistake. A response field costs tokens on every call forever and multiplies per edge case, while a narrowed enum or a corrected description costs nothing after the edit. Prefer shrinking the published surface over widening the payload, and fix the layer that PUBLISHES the contract, not the call site where the symptom showed up.

## ERROR/RETRY
Trust structured fields (error_name, ca_next_action, corrected_payload, accepted_aliases): identical deterministic payload failures may be blocked as DUPLICATE_RETRY_BLOCKED; UNSUPPORTED_FIELD/SCHEMA_VIOLATION→fix payload retry once; accepted_aliases present→retry with alias mapping (no escalate); 2nd retry still fails→report user with original+corrected payload, do NOT loop further. ## AUTO-CHAIN (pointer)
[A] auto-chains lightweight hints between tools to reduce round-trips. These are CA-level recommendations, NOT automatic execution. TWO field vocabularies exist in the code and this file used to declare only the rarer one: (1) ca_hint plus the scoped variants ca_hint_commit, ca_hint_rule, ca_hint_rule_text, ca_hint_review, ca_hint_scope -- the common form, emitted by most tools; (2) ca_chain_hint / ca_chain_next -- the rarer form, emitted only by the search and graph tools. Do NOT memorize how many chain fields there are or which files emit them: the authoritative list is AUTO_CHAIN_RULES in code_tools.py, which names every field with its trigger and its emitting module, and tests/test_a31_autochain_registry.py fails if the code, that registry, or this file drift apart. ca_next_action is NOT a chain field and NOT an enum: it is free-form advisory prose carried on both ok and error payloads, so read it and act on it, never match it against a fixed table of values. Read whichever key the payload actually carries. If a payload key and this file disagree, the payload wins and this file is the bug: never rename an emitted field to match a doc. Key chains:
- cbm_dead_code/cbm_test_gap/cbm_what_if -> auto-index if graph stale (_ensure_graph_fresh). The tool names carry the cbm_ prefix; a bare test_gap or what_if is a 404.
- write_fix (.py) -> ruff_preview in response (lint preview, not auto-fix)
- search_code -> ca_hint for read_file_range when results have line numbers
- search_code regex on root -> ca_chain_hint + ca_chain_next to narrow scope (search.py emits it on all three paths: timeout, runtime-guard and normal)
- cbm_dead_code -> ca_chain_next write_fix, AND ca_chain_precondition + resolution_limits (A35): "dead" means NO RESOLVED reference, never "unused" -- the graph resolves a call edge only through an imported module/alias, so self.fn() / obj.fn() / cfg.helper() leave the definition with zero inbound calls edges. Cross-check every entry with search_code(query='<name>', project_path='<abs>', mode='callers') -- a regex scan that DOES see instance receivers -- BEFORE deleting anything; cbm coverage -> ca_chain_next cbm_quality_gate (graph/tools.py)
- git_commit -> post_commit_validation in the response: a post-hook validates the files that were just committed. There is NO pre-hook injecting the hash, so you pass expected_staged_hash yourself -- and the cheapest source is the git_stage response you already have (after.staged_hash), NOT a fresh git_status. git_status.staged_hash is the right source only when you staged nothing in this turn.
- ruff_fix apply -> post_ruff_validation in response
- validate_file -> ca_hint for ruff_fix when ruff_fix_applicable
- git_status staged>0 -> ca_hint + ca_next_action "git_commit" (NOT git_stage -- those files are already staged)
- git_diff with a non-empty diff -> ca_hint + ca_next_action DERIVED from the payload's own scope: scope=staged -> "git_status then git_commit" (git_commit needs the expected_staged_hash git_status mints), any other scope -> "git_stage" with explicit paths. An empty diff carries NO hint key at all.
- write_fix / write_new_file ok -> ca_hint_commit for git_stage
- write_fix / write_new_file on a RULE file (examples/CORE_RULE.txt, SLIM_RULE.txt, SLIM_RULE_INLINE.txt) or on a REGISTRY file (code_tools.py, orchestrator/core/registry_data.py) whose new text touches TOOL_MAP / PROTECTED_TOOL_NAMES / TOKEN_REQUIRED_TOOLS / register_tool -> ca_hint + ca_next_action "rule_drift_check". Deliberately NOT every write: the predicate is rule_drift_trigger_reason in code_tools.py and it reads the SAME RULE_DRIFT_SOURCES tuple rule_drift_check itself reads, so a fourth rule file cannot leave the trigger silent on the one edit it exists to catch. A rule file matches by PATH alone; a registry file only by path AND symbol, because a path-only test would fire on every code_tools.py edit and a content-only test on every file that merely mentions TOOL_MAP. ca_next_action is a setdefault here, so when the same response also carries the cache_delta hint that one wins -- a desynced cache breaks your NEXT read, drift only the next campaign. This reaches THREE write tools, not two: write_fix_html and replace_between_anchors delegate to write_fix and inherit its hints verbatim.
- rule_drift_check with drift_count>0 -> ca_hint + ca_next_action "write_fix", closing the loop the line above opens. Read drifts[].code_value BEFORE you edit the doc: every row carries the live code value because the CODE is sometimes the side that moved, and a hint that always blamed the doc would launder a real code bug into a doc edit. A clean rule set carries no hint key at all.
- audit_tool_matrix with drift_count>0 or progressive_gap_count>0 -> ca_hint + ca_next_action "rule_drift_check" (it says which side moved), stamped AFTER the verbosity filter so the key cannot be pruned out of the very response it was written for -- an advisory that survived only at verbosity="full" would make its own absence read as "no drift". progressive_matrix_check with a non-empty gaps[] -> ca_hint + ca_next_action DERIVED from the gap area: a schema gap points at audit_tool_matrix, a workflow_docs or ui gap at read_file_range on the file gaps[].detail names. ok_to_ship_static_matrix=true carries no hint.
- write_draft_patch that still fails -> ca_hint + ca_next_action "write_draft_patch" on the DRAFT_STILL_FAILING payload (ca_next_action is valid on errors, and this is what that is for), and write_draft_status -> the same whenever a listed draft, or the one you asked for, is failing. A draft is a HELD write: it ships NOTHING when its TTL expires, so write_draft_abort is the deliberate exit, never the default.
- git_stage -> ca_hint naming after.staged_hash + ca_next_action "git_commit". The expected_staged_hash git_commit demands is ALREADY in the git_stage response, one level down, so a second call to fetch it is pure waste: measured 2026-09-20, a CA probed fields=staged_hash on git_stage, got fields_unknown, concluded the field did not exist and paid for a git_status anyway.
- git_stage/git_commit -> ca_hint_review for ocr_review (a string only, never spawns a review)
- ocr_map -> ca_hint_map: files[] is ordered by changed-line count and excluded_summary names every drop reason (a string only, zero LLM, zero token)
- open_session resume that rejects BOTH the requested title AND the mode -> ca_next_actions (PLURAL), a LIST naming both owed actions, next to resume_rejected. Read the plural on THIS payload: ca_next_action holds one string, so the title branch used to overwrite the mode's action and the caller fixed the title never learning the mode had not applied (ISS-08). The singular still carries the title action alone, and ca_next_tool is derived from that singular, so the mode divergence is visible ONLY in the list. It is a registry row while the free-form singular is not for the reason stated above -- it is structured, emitted at one site under one condition. Do not 'tidy' it away as a duplicate: deleting it reopens ISS-08.
- PASSIVE table -> ca_hint + ca_next_action for tools that emit NO hint of their own. The rows live in ONE place, orchestrator/core/passive_chain.py (PASSIVE_CHAINS; the covered tools are PASSIVE_CHAIN_TOOLS, derived from it -- read the module, this line deliberately does not copy the list). Applied once at the dispatch funnel for every tool, so ca_next_tool below derives from it exactly as it does from a hand-written hint. Three properties you can rely on: it fires ONLY on ok:true (an error keeps whatever ca_next_action its own handler chose), it NEVER overwrites a hint the tool wrote itself (a tool that set either key keeps both -- mixing two authors produces advice neither meant), and it obeys your fields= projection (a key you did not ask for is not added). A row whose condition does not hold is simply silent: the ABSENCE of a passive hint is not an assertion that nothing is worth doing next.
- ANY tool -> ca_next_tool, whenever that tool's ca_next_action really names a live tool. THIS IS THE TOOL-NAME / HINT SPLIT and it is the field to read before you chain: ca_next_action is prose that MAY contain a tool name; ca_next_tool is emitted ONLY when that name exists in the live registry. Measured 2026-09-18: 25 ca_next_action literals name a real tool inside the advice ("use_write_fix_or_choose_new_path") and 26 more are the identical snake_case shape while naming no tool at all ("use_partial_then_narrow_regex_scope"). So NEVER lift a snake_case run out of ca_next_action and call it -- ca_next_tool present => callable, ca_next_tool ABSENT => ca_next_action is advice to READ, not a tool to CALL. It is derived per response from the live TOOL_MAP (orchestrator/core/next_tool.py), so it follows tool add/remove with no doc edit, and a value that points at the tool you just called survives only when the prose actually says call/use/run -- a status sentence that happens to open with its own tool name is an echo, not an instruction.
- ANY caller -> pipeline=[...] on read_file_range or search_code. This is the ACTIVE half and the ONLY half that RUNS anything, so read the boundary carefully: nothing runs unless the call itself names the steps. That is why it is not the automatic execution this section forbids -- it is a read YOU asked for, batched into the answer you were already waiting on, and a tool never adds a step you did not list. Every step is a READ, proven against the live _MUTATING_TOOLS set rather than a list in a doc, so a target that gains a write tomorrow fails the suite instead of shipping. Every payload is built from THIS call's own result -- the neighbour range it already computed, the file holding the first match -- never from something you must pass twice. Do NOT memorize the step names or how many there are: the enum in each tool's own schema IS the list, derived from ACTIVE_CHAIN_STEPS in orchestrator/core/active_chain.py, and a name that is not in it is echoed back under pipeline.rejected next to the steps that did run, never raised. The answers land under the response key `pipeline`, which accounts for EVERY step you asked for: ran / skipped (its input was not in this result) / failed, plus dropped when you ask for more than MAX_STEPS_PER_CALL -- a truncation is always NAMED, never silent, so a short report is never a claim of full coverage. An unset pipeline costs nothing, and a fields= projection that does not ask for `pipeline` skips the reads entirely instead of running them and throwing the report away.
Do NOT auto-execute ca_next_action / ca_next_tool / ca_chain_next without user go-ahead; present as suggestion. That covers a hint that names a pipeline step too: pipeline= runs only what the CALLER listed, so acting on a hint by adding one still needs the go-ahead like any other chained call.
